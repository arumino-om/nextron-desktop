## 2. 両仕様から読み取った構造

決定ではなく、現状理解。設計判断の前提となる。

### 2.1 四層アーキテクチャ

BTRON3 第2編1章の名称が「周辺核」である理由は、その下に中心核があるため。

```
┌───────────────────────────────────────────────────┐
│ アプリケーション / システムアプリケーション           │
├───────────────────────────────────────────────────┤
│ 外殻 (Shell) 11マネージャ + ディスプレイプリミティブ │ BTRON3 第2編 2・3章
│ アプリケーションライブラリ / 標準ライブラリ          │ BV 第3編
├───────────────────────────────────────────────────┤
│ 周辺核 (Peripheral Kernel)                          │ BTRON3 第2編 1章
│   プロセス/タスク・ファイル・メモリ・イベント・デバイス │ + BV 第1編の差分
│   ★ ページングによるメモリ保護はここが行う             │
├───────────────────────────────────────────────────┤
│ 中心核 I-right/V = μITRON3.0 レベルE 完全実装         │ BV 第5編
│   タスク・セマフォ・イベントフラグ・メイルボックス     │ ← ItIs Phase3 派生
│   メッセージバッファ・ランデブ・割込・時間管理         │
│   ★ メモリ保護は一切しない                            │
├───────────────────────────────────────────────────┤
│ デバイスドライバ = ITRON タスク群                     │ BV 第4編
│   ランデブポートで OPEN/CLOSE/READ/WRITE/ABORT/      │
│   SUSPEND/RESUME/CARDEVENT/USBEVENT を受付           │
└───────────────────────────────────────────────────┘
```

### 2.2 B-right/V の 32bit メモリモデル（踏襲しない）

- セグメントは 7 本あるが全部 base=0 / limit=4GB のフラット。
  仕様書は「いずれの保護レベルからでもすべてのメモリーにアクセスすることが可能である
  **(メモリー保護は働かない)**」と明記
- 保護は周辺核がページングで行う
- **タスク固有空間 0〜256MB、256MB〜4GB は全タスク共有**
- 切替方式: ページディレクトリは世界に 1 枚だけ。タスクスイッチ毎に
  先頭 64 PDE (= 256 バイト) をコピー

##### なぜこの形だったか

| 値 | 決めた要因 |
|---|---|
| 固有空間 256MB | **タスクスイッチのコピー量**。64 PDE × 4MB = 256MB、64 × 4byte = 256B。固有空間を広げるとコピー量が正比例で増える |
| 共有空間 3.75GB | **余り**。目標値ではない |

PDE コピー方式を採った理由（CR3 切替ではなく）:

1. **中心核にページングを理解させないため。** ITRON は不透明な 256 バイトを memcpy
   するだけで、共有領域の存在もプロセスの概念も知らなくて済む
2. **共有領域の正本が 1 つになるため。** 共有メモリは `get_mbk(M_COMMON)` で実行時に
   動的確保されるので、タスク毎に完全なページディレクトリを持つ方式では
   新しい PDE 値が実行中に発生し、全タスクへの伝播が必要になる。
   1 枚にすれば伝播先が存在しない
3. TLB は理由にならない。i386 には PDE 配下だけを選択的に流す命令がないので、
   PDE 書き換え時も結局 CR3 リロードで全フラッシュする

**64bit ではこれらの制約が全て消える**（§3.2 参照）。

### 2.3 外殻は「ユーザランドのライブラリ」ではない

- BTRON3 は外殻の API を自ら「**拡張システムコール**」と呼んでいる
- I-right/V に `def_svc()` と `int 129` (拡張 SVC 呼び出し) があり、呼び出し時に
  保護レベルが変わる
- IOPL=1 なので保護レベル 0/1 は全 I/O アクセス可、2/3 は不可

つまり外殻は**アプリと同じアドレス空間に居て、トラップで特権を上げて入るカーネル側のコード**。
モノリシックカーネルの配置。したがって「外殻をユーザランドへ」はモノリシック →
マイクロカーネルの作り替えになる（E1）。

### 2.4 B-right/V が実装しなかった仕様機能

実装の優先順位付けに直接使える情報。

| 層 | 未実装 / 制限 |
|---|---|
| DP | 描画環境のプレーン数は **1 のみ** |
| DP | 有効ピクセルビット 1/2/4/8/16/24、境界 1/2/4/8/16/32 のみ。8bit 超はリトルエンディアン |
| DP | **マスクピクセル値 未サポート** |
| DP | **ビットマップ圧縮 (MH/MR符号) 全面未サポート**（`gcom_bmp`/`gunc_bmp`/`gsiz_cbm` は常に `EG_NOSPT`） |
| 周辺核 | **`def_exc` / `ret_exc` 未サポート**（例外処理ハンドラ機構が無い） |
| 周辺核 | **`get_cnf` 未サポート**。システム管理機能は `get_ver` のみ |
| 周辺核 | **ファイルのパスワード機能 未サポート**（`chg_fpw` 未実装、`opn_fil`/`chk_fil` の pwd は無視） |
| 周辺核 | `map_rec()` はリムーバブル媒体と論理ブロック 4KB 未満の FS で使用不可 |
| 外殻 | **ウィンドウ / メニューの表示属性 `atr` の指定は無視**（デザイン・色はシステム規定）。代わりに `WI_*` ウィンドウ情報レコードが全体テーマを一元管理 |
| 外殻 | **パーツの点滅 `P_BLINK` 未サポート**（指定すると `EX_PAR`） |
| 中心核 | `dis_int`/`ena_int`/`def_exc`/`chg_ims`/`ref_ims` 非サポート |
| 中心核 | メモリプール機能（可変長・固定長）を使わない（メモリは周辺核が管理） |

B-right/V が**追加**したもの: `prc_inf` / `req_emg` / `syn_fil` / `lod_mod` / `unl_mod`、
DMA 専用メモリ `M_DMA`、グループ主ウィンドウ `WA_GROUP`、`WA_THIN` / `WA_NOFRAME`、
TIP 候補選択ポップアップ `ipup_sel`、文字のグレースケール描画、FD 拡張形式2。

### 2.5 TRONコードの面構造

**Unicode は TRONコードの一部分として内包されている。** したがって
「TRONコード準拠か Unicode 内部化か」は二者択一ではない。

| 面 | 内容 | 言語指定コード |
|---|---|---|
| 1 | システムスクリプト: JIS X 0208 + 0213第3/第4水準 + 0212補助漢字 + 六点/八点点字 + GB2312 + KS X 1001 | 0xFE21 |
| 2–3 | GT書体フォント 96,800字 | 0xFE22, 0xFE23 |
| 6–7 | CNS-11643 全7面（中国伝統字） | 0xFE26, 0xFE27 |
| 8–9 | 大漢和辞典 51,110字 + 記号文字類（iモード絵文字・ホツマ文字・陰陽五行・序数記号・アーヴ文字） | 0xFE28, 0xFE29 |
| 10 | 中国伝承文字・少数民族文字（トンパ文字） | 0xFE2A |
| **16–17** | **Unicode BMP 65,536字** (U+0000–U+ABFF → 0xFE30 / U+AC00–U+FFFF → 0xFE31) | 0xFE30, 0xFE31 |
| 18–31 | 予約 | 0xFE32–0xFE3F |

逆に内部を Unicode にすると、GT書体 96,800字と大漢和 51,110字が表現できなくなる。

## 3. 決定済み事項

### 3.1 ILP32 厳密準拠は選択肢から除外

**状態: `決定`**

- arm64 では **ARMv9 世代の多くのコアで AArch32（32bit 実行状態）が実装されていない**
  （Cortex-A715/A720/A520、Cortex-X3/X4、Neoverse N2/V2 など）。
  ハードウェアレベルで 32bit 実行の選択肢が無い
- 代替の ILP32 ABI は、AArch64 ILP32 が Linux 本体に未取り込み、
  x86_64 の x32 ABI も実質メンテナンスされていない
- x86 の 32bit 互換モードは今も動くが、arm64 対応を捨てることになる

→ 64bit 化は前提条件。ただし**拡張の範囲**は未決（A1）。

参考: 32bit が現役なのはマイコン領域（Cortex-M / RV32 / ESP32）で、
μITRON / μT-Kernel が実際に生きている場所。TRON 系譜の ITRON 側は 32bit のままで
問題なく、BTRON のような GUI 汎用 OS は 64bit 側にしか居場所がない。

### 3.2 アドレス空間レイアウト

**状態: `決定`**

1. **下位カノニカル半分 128TB = プロセス固有空間**（ローカルメモリ、正のアドレス）
   **上位カノニカル半分 128TB = 共有空間**（共有/システムメモリ、負のアドレス）
   → BTRON3 §1.5「共有・システムメモリは負、ローカルは正」を満たす。
   32bit 時代より 64bit でこそ自然に実現できる

2. **両アーキで上位半分の基底を `0xFFFF_8000_0000_0000` に統一**

   既定値は食い違う（x86_64 は各半分 47bit = 128TB、arm64 は T0SZ=T1SZ=16 で
   各半分 48bit = 256TB）。**arm64 側で `TCR_EL1.T0SZ = T1SZ = 17`** に設定すると
   TTBR1 領域が `0xFFFF_8000_0000_0000` からの 2^47 = 128TB になり完全一致する。
   アドレス定数の `#ifdef` 分岐が 1 つも要らなくなる

3. **上位半分の区画は 512GB (= 1 PML4 エントリ) 境界に揃え、固定アドレスとする**

```
0xFFFF_8000_0000_0000  ┌──────────────────────────────┐ ← 上位半分の先頭 (PML4E #256)
                       │ 物理メモリ ダイレクトマップ    │  32TB   (64 PML4E)
                       │   核が任意の物理ページに触る用 │
0xFFFF_A000_0000_0000  ├──────────────────────────────┤
                       │ 共有メモリ領域  M_COMMON      │  32TB   (64 PML4E)
                       │   get_mbk(M_COMMON) の供給元  │
0xFFFF_C000_0000_0000  ├──────────────────────────────┤
                       │ システムメモリ領域 M_SYSTEM   │  16TB   (32 PML4E)
                       │   ドライバ専用                │
0xFFFF_D000_0000_0000  ├──────────────────────────────┤
                       │ map_rec() マッピング領域      │   8TB
                       │   F_COMMON / F_SYSTEM の宛先  │
0xFFFF_D800_0000_0000  ├──────────────────────────────┤
                       │ MMIO / フレームバッファ        │   8TB
0xFFFF_E000_0000_0000  ├──────────────────────────────┤
                       │ 予約                          │
0xFFFF_FF00_0000_0000  ├──────────────────────────────┤
                       │ 中心核 / 周辺核 コード・データ  │
0xFFFF_FFFF_FFFF_FFFF  └──────────────────────────────┘
```

   ダイレクトマップの 32TB が扱える物理メモリの上限になる。

4. **上位半分の最上段エントリは起動時に全数確保し、以後不変とする**

   これは**不変条件**。破れると全プロセスのページテーブル走査が復活する。
   守る方法: 起動時に上位 256 エントリ分の PDPT を全部確保する（256 × 4KB = **1MB**）。
   以後、共有領域への追加マップは全て PDPT より下で起きるので最上段には届かない。
   起動時に 1MB 払って同期問題を買い取る取引。

   | | コピーする物 | いつ | 量 |
   |---|---|---|---|
   | B-right/V (i386) | **固有空間**の PDE 64個 | **毎タスクスイッチ** | 256 B |
   | 本OS x86_64 | **共有領域**の PML4E 256個 | **プロセス生成時に1回** | 2 KB |
   | 本OS arm64 | 何もコピーしない（TTBR1 を起動時に設定） | — | 0 |

   複製されるのは最上段のポインタ値のみ。その下の PDPT / PD / PT と実メモリは
   **1 組しか存在しない**ので、PTE/PD/PDPT レベルの変更は全プロセスに即座に見える。

5. **アーキ差分は 2 関数に閉じる**

```
arch_create_address_space():
  arm64 : TTBR0 用のツリーを確保するだけ
  x86_64: PML4 を確保し、上位 256 エントリを雛形から memcpy

arch_switch_address_space():
  arm64 : TTBR0_EL1 <- (ツリー物理アドレス | ASID)
  x86_64: CR3       <- (PML4 物理アドレス  | PCID)
```

   ASID (arm64, 8/16bit) と PCID (x86_64, Westmere 以降) により、
   アドレス空間切替で TLB が流れない。

### 3.3 文字コードは TRONコード面構造を採用

**状態: `決定`**（内部表現は未決 = B1）

- TRONコードを正とし、面構造をそのまま採る
- Unicode は第16–17面として内包される（§2.5）
- Unicode SMP 以降（U+10000〜、絵文字など）は**第18面以降に新規割り当てして拡張**する
  （予約が 0xFE32–0xFE3F の 14 面分ある）

### 3.4 ファイルシステムは拡張形式2 準拠 + 64bit 拡張

**状態: `決定`**（具体値は未決 = C1〜C3）

- FD 拡張形式2（`TRONディスクID 0x52FE` / `ディスク形式ID 0x6402`）に準拠
- **拡張形式2 は読み書き両対応にする。** 超漢字の実データで検証できる唯一の領域
- 64bit 拡張を「拡張形式3」として定義する（`f_id` / `f_size` / `STIME` / `fs_nblk`）

拡張形式2 自体が R4 での拡張なので、**仕様を拡張形式として拡げるのは
パーソナルメディア自身がやったこと**。前例に沿う。

拡張形式2 の変更点: FS 総容量 4GB 超対応 / `DfFragment2.blk` を UW に /
参照カウント `refcnt` を W に / レコードインデックス開始位置 `ridxofs` 可変化
(`(192+16) <= ridxofs <= 論理ブロックサイズ-16`) / `FS_STATE.fs_bsize` を H→UH /
論理ブロックサイズの「2のべき乗」制限を「物理ブロックサイズの倍数」に緩和。

### 3.5 外殻アーキテクチャ

**決定 (2026-10-11): 外殻をサーバ群とプロセス内ライブラリに分割する。**

分析の全文は **詳細 E1**。ここは結論のみ。

#### (a) 配置

```
サーバ化（粗い呼び出し + グローバル状態）
  ウィンドウマネージャ / トレー / 実身仮身 / 印刷 / TCP-IP

プロセス内ライブラリ（細かい呼び出し + 固有状態）
  DP（ウィンドウごとのバックバッファが条件）/ パーツ

二分（ロジックはプロセス内、面と入力の占有は WM サーバ）
  メニュー / パネル

中間（読み出し専用共有メモリ + 操作だけサーバ）
  フォント / データ / TIP
```

#### (b) WM サーバが提供する「面」は 3 種類

```
① 通常ウィンドウの面            （主 / 従属 / 前面）
② ポップアップ面 + 入力グラブ    <- メニュー・パネル・TIP 候補選択が共用
③ システムメッセージパネル        （唯一・WM 専有）
```

#### (c) IPC

```
制御メッセージ   BTRON3 §1.3 のランデブを拡張した同期 RPC
                 cal_por / acp_por / fwd_por / rpl_rdv の意味論を維持
                 ＋ アドレス空間跨ぎ ＋ 優先度継承 ＋ ハンドル渡し ＋ SMP
```

#### 詳細 A1/A2/A5 — 最小拡張方式とその帰結

**決定 (2026-10-11): `W` = 32bit 維持。溢れるフィールドのみ 64bit 型で拡張する。**

##### 採用理由

- 全構造体のレイアウトと API シグネチャが大半で保たれる = **仕様適合性が最大**
- エラーコード・各種 ID・優先度・フラグ・`COLOR`(28bit) は本質的に 32bit で足りる
- 拡張形式2 との互換が取りやすい
- **副産物**: 超漢字のアプリケーションの**ソースが多くはそのまま再コンパイルで通る可能性がある**。
  壊れるのは「ポインタを `W` に入れていた箇所」と「ポインタを含む構造体を直接 I/O していた箇所」のみ。
  これは `W`=64bit 案では得られない利点

##### 64bit 化が必須なフィールド

**(a) 値が溢れるもの**

| 分類 | フィールド |
|---|---|
| ファイル | `F_STATE.f_size`（2GB 上限）, `f_nblk` |
| FS | `FS_STATE.fs_nblk`, `fs_nfree`, `fs_nfile`（現 `UH`、A2 と連動） |
| 時刻 | `STIME` と全利用箇所: `f_ltime` `f_atime` `f_mtime` `f_ctime` `fs_mtime` `fs_ctime` `F_LINK.rf_ctime` |
| プロセス | `P_INFO.tmem` `wmem`（バイト単位。2GB 上限は論外）, `utime` `stime`（ms 累計。2^32 ms ≒ 49 日） |
| レコード I/O | `see_rec` `rea_rec` `wri_rec` `ins_rec` `apd_rec` `trc_rec` `map_rec` の `offset` / `size` |
| デバイス I/O | `rea_dev` / `wri_dev` の `start`（ブロック番号）, `size` |
| メモリ | `M_STATE.blksz` `total` `free` |

**(b) ポインタが `W` に入っている箇所** ← 見落としやすい。`W`=32bit では**必ず壊れる**

| 箇所 | 内容 |
|---|---|
| `M_EXECREQ.info` / `M_DISPREQ.info` / `M_PASTEREQ.info` / `M_FUSENREQ.info` / `M_TADREQ.info` | 「実身/仮身マネージャで管理している**付箋の固有データへのポインタ**」 |
| `cre_tsk(FP entry, W pri, W arg)` の `arg` | タスク起動パラメータ。ポインタを渡すのが常道 |
| `GEVENT.src` | `W src; /* ソースPID/他 */` の「/他」 |
| `cre_nam(TC *name, W data, W opt)` の `data` | 仕様は「1つの32ビットデータ」と明記 → A12 |

**(c) 32bit で十分（判断の記録）**

`F_STATE.f_nrec`（総レコード数、21億）/ `f_nlink` / `DfFileHeader.refcnt`（参照カウント）/
プロセス ID・タスク ID・各種 ID / 優先度 / エラーコード / `COLOR`（28bit 使用）

##### ポインタを含む構造体は、どの選択でもサイズが変わる

`W` の決定とは無関係に、以下は 64bit 化でレイアウトが変わる。

`PAT`（`UB *mask` `BMP *bmap` `UB *pat`）/ `BMP.baseaddr[]` / `RLIST.next` /
`GRGN.s[].hp` / `CSPEC.colmap`

`W`=32bit を選ぶと**被害がポインタ含有構造体だけに限定される**。これも採用理由の一つ。

##### A2 の帰結

```c
typedef struct {
    TC  fs_name[L_FSNM];    /* 20 TC = 40 byte */
    UW  f_id;               /*  4 byte  <- UH から拡張 */
    UH  atr1 .. atr5;       /* 10 byte */
} LINK;                     /* 56 byte 確定 (54 が align 4 で丸められる) */
```

1. 仕様は「**LINK 構造体のサイズ (52バイト)**」をリンクレコードのレコードサイズとして
   アプリに返す値として規定している。変わることを明記する必要がある
2. 仕様の「ファイルIDは 16 ビットの数値で表わされるため、最大ファイルIDは 65535 を
   越えることはできない」という記述を**覆す**。拡張形式3 の定義として明示的に上書きする
3. **拡張形式2 との互換は素直に取れる。** 拡張形式2 は最大 65,535 実身なので
   ディスク上の 16bit `f_id` で足る。読込時はゼロ拡張、書込時は `f_id > 65535` でエラー
4. **オンディスクのリンクレコード構造が未確認**（固定リンクは `fs_name` を持たないので
   ディスク上はもっと小さい）→ §5 の要調査項目

#### 詳細 A7 — メモリ表現とディスク表現の分離

**決定 (2026-10-11): ディスク・TAD・交換媒体に出る構造体は、メモリ構造体とは別に
ディスク表現記述を持つ。構造体の直接 I/O（`fwrite(&st, sizeof st, 1, fp)`）は禁止。**

##### なぜ必要か

構造体のメモリ上の並びは**コンパイラが決める**が、ディスク上の並びは**仕様書が決める**。
3つの食い違いが起きる。

1. **パディング** — A1 の 64bit 化で `D` 型が入ると 8 バイト境界を要求する。
   フィールドを足したり並べ替えると、コンパイラが勝手に隙間を入れ、
   仕様書が定めたオフセットからずれる
2. **`#pragma pack(1)` で潰すと別の問題** — パディングは消えるが**未アライメントアクセス**に
   なる。arm64 は通常のロード/ストアなら許容するが、アトミック操作や一部 SIMD 命令で
   例外が出る。最適化も効かない
3. **エンディアン** — A4 で「内部リトル / 標準形式ビッグ」と決めたので、
   標準形式の読み書きには全フィールドのスワップが必要。
   構造体を直接 I/O すると変換を挟む場所がない

##### 構造

```
[メモリ表現]   自然なアライメント / CPU エンディアン / コンパイラ任せ
      <->      明示的なシリアライザ・デシリアライザ
[ディスク表現]  仕様書が決めたバイト並び / パディングなし / 指定エンディアン
```

##### 実装方式: テーブル駆動（推奨）

```c
typedef enum { F_U8, F_U16, F_U32, F_U64, F_BYTES } FieldKind;
typedef struct {
    FieldKind kind;
    UH        off_mem;      /* offsetof() で取る */
    UH        off_disk;     /* 仕様書の値を手で書く */
    UH        len;
} FieldDesc;

static const FieldDesc df_fileheader_desc[] = {
    { F_U32,   offsetof(DfFileHeader, startid),  0, 4 },
    { F_U16,   offsetof(DfFileHeader, ftype),    4, 2 },
    { F_BYTES, offsetof(DfFileHeader, own),      8, 28 },
    /* ... */
    { F_U64,   offsetof(DfFileHeader, size),    96, 8 },
};
```

汎用のローダ・セーバ 1 組で全構造体を処理できる。利点:

- **`off_disk` の列が仕様書の表そのまま**になるので、仕様と突き合わせて検証できる
- `static_assert` でディスク側の総サイズを検証できる

##### BV の前例

`ConvEndianStruct(VP to, VP from, char *form, W max)` の `form` 文字列がまさにこれ。

```
b  B タイプ      h  H タイプ      w  W タイプ
t  3バイト       p  B サイズのパディング
前に 10 進数を置くと繰り返し回数    例: "w2h28b2h2h"
```

**パーソナルメディアも同じ結論に達していた。** `d`（64bit）を追加して拡張するのが筋。

##### 適用範囲

| 分離が必要 | 不要（素の構造体でよい） |
|---|---|
| FD 形式の全構造（システムヘッダ / ファイルIDテーブル / ファイル短縮名テーブル / ビットマップ / ファイルヘッダ / フラグメントテーブル / レコードインデックス） | `EVENT` `WEVENT` `BMP` `PAT` `RECT` `SIZE` `PNT` |
| TAD の全セグメント | `P_STATE` `P_USER` `P_INFO` `M_STATE` |
| **`LINK`**（リンクレコードとしてディスクに出る） | `FSSPEC` `FNTINFO` `TIPREC` |

#### 詳細 A13 — ページサイズ

**状態: 要判断。推奨は 4KB。**

##### 決定的な制約: x86_64 に 16KB ページは存在しない

```
arm64   granule 4KB / 16KB / 64KB から選択可
x86_64  4KB 固定（+ ヒュージページ 2MB / 1GB）
```

16KB を選ぶとアーキ間でページサイズが揃わず、x86_64 では
「4KB ページを 4 枚束ねて 16KB として扱う」上位抽象を自作することになる。

##### §3.2 のアドレス空間設計が崩れる

```
arm64 4KB granule, 48bit VA
  L0(9bit, 512) -> L1(9bit) -> L2(9bit) -> L3(9bit) -> offset(12bit)
  1 L0 エントリ = 512GB        <- §3.2 の「512GB 境界」はこれ
  上位半分 = 256 エントリ      <- §3.2 の「2KB 複製」はこれ

arm64 16KB granule, 48bit VA
  L0(1bit, 2!) -> L1(11bit, 2048) -> L2(11bit) -> L3(11bit) -> offset(14bit)
  1 L0 エントリ = 128TB /  1 L1 エントリ = 64GB
  L0 は 2 エントリしかない
```

**L0 が 2 エントリしかないので「上位 256 エントリを確保して 2KB 複製」が成立しない。**
区画境界も 512GB ではなく 64GB 単位になる。arm64 は TTBR1 があるので実害は限定的だが、
x86_64 は 4KB のままなので**両アーキの設計が別物になり、
§3.2 の「アドレス定数の `#ifdef` 分岐がゼロ」という利点が失われる。**

##### `map_rec()` が使えなくなる

BV の制限「論理ブロックサイズが 4KB 未満の FS では `map_rec()` できない」は
**ページサイズ単位でマップするから**。

```
ページ 16KB -> 論理ブロックサイズも 16KB 以上でないと map_rec() が使えない
拡張形式2 の標準 FD は論理ブロック 1024 バイト -> map_rec() 不可
```

さらに論理ブロック 16KB は小さいファイルで**内部断片化が増える**。
BTRON の実身は「文書と仮身が大量」想定なのでここは効く。

##### その他

- `get_mbk(nblk)` の単位がページサイズ。`M_STATE.blksz` としてアプリに公開される（A14 に波及）

##### 16KB で得られるもの（公平に）

- **Apple Silicon でネイティブ**（macOS は 16KB ページ）
- TLB エントリ 1 個のカバー範囲が 4 倍 → TLB ミス減
- ページテーブルが浅く小さい / ページ管理メタデータが 1/4

##### 決定 (2026-10-11)

**4KB。** ただし以下の規律を併せて設ける（**規律 R2**、§8）。

> **ページサイズを定数としてハードコードせず、HAL が公開する値として参照する。**

これを守れば、後から「16KB をスーパーページとして扱う」最適化として追加できる
（Linux が THP で 2MB を後付けしたのと同じ発想）。

16KB へ移行する判断が必要になった時点で、§3.2 のアドレス空間設計（512GB 境界 /
上位 256 エントリ / 2KB 複製）を arm64 側だけ再設計することになる。
その影響範囲は 詳細 A13 の上記分析がそのまま使える。

#### 詳細 A3/B1 — 文字コードの内部表現

**決定 (2026-10-11): 境界は 16bit `TC`（ステートフル）、内部処理は 32bit `WTC`（ステートレス）。**

BV が実装済みの三層構造をそのまま採る。

| 型 | 幅 | 性質 | 用途 |
|---|---|---|---|
| **`TC`** | 16bit (`UH`) | **ステートフル** — 面は言語指定コード (0xFE2x) が文字列中に埋め込まれて運ぶ | TAD・ファイル名・API 表面・保存・交換 |
| **`TLANG`** | 16bit (`UH`) | 言語指定コードの**短縮形**。`0xAABB`、AA = 0xFE の繰り返し数−1、BB = 後続コード | 面の識別 |
| **`WTC`** | **32bit (`W`)** | **ステートレス** — 1文字が1つの値 | **内部処理**（検索・カーソル移動・ソート） |

```c
typedef UH      TC;         /* TRON 文字コード */
#define TNULL   ((TC) 0)

typedef UH      TLANG;      /* 言語(スクリプト)指定コードの短縮形 */
#define TSC_SYS         0x0021  /* システム */
#define TSC_JPN1        0x0022  /* 日本1 */
#define TSC_JPN2        0x0023  /* 日本2 */
#define TSC_MIN         0x0021
#define TSC_MAX         0x003f

/* 短縮形の規則:  FE21 -> 0x0021 / FEFE 0021 -> 0x0121 / FEFE FE21 -> 0x0221 */

typedef W       WTC;        /* ワイド TRON 文字 */
/* 0xxxxxxx xxxxxxxx yyyyyyyy yyyyyyyy
   上位15bit = TLANG、下位16bit = TC
   lang = 0      -> 言語非依存の文字（制御文字等）
   lang = 0x7fff -> 不正な言語指定コード                      */
#define towtc(lang, tc) (((WTC)(lang) & 0x7fff) << 16 | ((WTC)(tc) & 0xffff))
#define wtcchar(wtc)    ((WTC)(wtc) & 0x0000ffff)
#define wtclang(wtc)    ((WTC)(wtc) >> 16)
#define WTNULL          0
```

#### 詳細 A4 — エンディアンと準規格

**状態: 要判断。** 調査結果は確定。

##### BTRON3 自身がリトルエンディアン版を正式に規定している

| 規格 | 所在 |
|---|---|
| **準TAD規格** | BTRON3 第1編 第3章 **付録B** |
| **準標準フロッピーディスク形式** | BTRON3 第1編 第4章 **付録A** |

> TADデータ構成では、異なるプロセッサ間を含めたデータの互換性を完全に保証するために
> 8ビット以上のビット長を持つデータのバイトオーダーは、上位バイトが先にくる
> ビッグエンディアン形式に統一している。
> **しかしながら、この形式はリトルエンディアン形式の CPU 上で動作する既存の
> アプリケーションを移植する場合等には負担となる場合もあるため、これを救済するために、
> リトルエンディアンのデータ形式を持つTADデータ構成を、準TAD規格として規定する。**

そして BV のエンディアンライブラリ（`btron/cnvend.h`）にはこう書かれている。

> **ファイル内の TAD データは 1B に準拠して little endian になっているものとする。**

「1B」= 第1編 付録B = 準TAD規格。**つまり超漢字のファイルは準TAD規格（リトルエンディアン）。**

##### 準TAD規格の変更点

1. **文字コードは2バイト固定長、第2バイトが先。さらに 1バイトの制御コードの直後に
   常に値 `0` のバイトを詰める**
2. `H` `UH` `W` `UW` `COLOR` `UNITS` `CHSIZE` `SCALE` `RATIO` はリトルエンディアン
3. 可変長セグメントの形式もバイトオーダーが逆転
4. `UB` タイプには 1. の2バイト固定長文字コードのみ使用

**1. が重要。これは単なるバイトスワップではない。** 標準 TAD は1バイト制御コードと
2バイト文字が混在するが、準TAD は全部2バイトに揃えるので**文字ストリームの構造自体が変わる**。
素朴なバイト入れ替えでは変換できない。

##### 準標準FD形式の識別方法

> システムヘッダの TRON ディスク ID、およびディスク形式 ID のバイトオーダーにより、
> TRON 標準フロッピーディスク形式か、準標準フロッピーディスク形式かの識別が行なわれる。
> すなわち、BTRON標準の場合は、`0x42, 0xFE, 0x64, 0x00` であり
> **準標準の場合は、`0xFE, 0x42, 0x00, 0x64`** となる。

**マジックナンバー自身がバイトスワップされているので、それを見ればエンディアンが判る。**
追加フラグが不要。

##### 両規格が課す義務

- **標準形式との双方向変換機能を持つこと**
- 準規格である旨を明記すること
- 変換方法を明記すること

##### 決定 (2026-10-11)

```
システム内部・システムディスク : 準標準形式（リトルエンディアン）を正とする
                                 x86_64 / arm64 がリトルなので変換ゼロ
従来の TRON 向け記憶装置の I/O  : 標準形式（ビッグエンディアン）
                                 互換モードとして変換層を挟んで実装
TAD の交換用出力のデフォルト    : 標準形式（ビッグ）
                                 異機種間互換が TAD の存在理由
識別                           : マジックナンバーのバイトオーダーで自動判別
```

**変換層は「境界にのみ存在する」**という形にする。内部のデータ構造は一切変換を意識しない。

理由:

1. **超漢字の実データが準標準形式。** 拡張形式2 の読み書き互換（§3.4）を取るなら必須
2. リトルエンディアン機で標準形式を内部形式にすると**全フィールドアクセスに変換が入る**
3. 仕様が双方向変換を義務付けているので**両対応は避けられない**。
   どちらを内部形式にするかの問題にすぎない

#### 詳細 C1 — オンディスク形式（BTRON3 第1編 第4章 §4.3 読了）

##### 最大の発見: リンクレコードはデータブロックを持たない

レコードインデックス（**16 バイト**）には 4 形式あり、**先頭 2 バイトで判別**される。

| 形式 | 第1バイト | 第2バイト |
|---|---|---|
| 接続インデックス | ≠0 | any |
| 通常インデックス | =0 | ≠0 |
| **リンクインデックス** | **=0** | **=0x80** |
| 未使用インデックス | =0 | =0 |

リンクインデックスの中身 = レコードタイプ（`100T TTTT`, T=0）＋ **ファイルID** ＋ **属性データ1〜5**。

**固定リンクのディスク表現は 16 バイトのレコードインデックス 1 個だけで、
データブロックを一切使わない。**

これで仕様の記述が説明できる:

> リンクレコードの場合はレコードサイズ情報を持たないが、レコードの入出力に必要な領域の
> サイズである **LINK 構造体のサイズ (52バイト)** をレコードサイズとする。ただし、
> このリンクレコードのサイズは、ファイル管理情報としての総バイト数には、カウントされない。

**52 バイトは API のためのメモリバッファサイズであってディスクサイズではない。**
`f_size` に数えないのは、ディスク上にデータが存在しないから。

```
 384 - 1023   レコードインデックス 40x16  640   <- 「最大40個」の根拠
```

##### 拡張形式3 で必要な変更（確定）

**① ファイルヘッダ: 192 -> 256 バイト**

```
64bit 化の増分:  総バイト数 +4 / 総ブロック数 +4 / 日時4種 +16 / ファイルID +2 = +26
予約 16 では 10 バイト不足
```

256 バイトを推奨。2 のべき乗で `ridxofs` の 16 バイト境界制約とも整合し、将来の余地も残る。

**② レコードインデックス: 16 -> 32 バイト**

リンクインデックスに空きがゼロなので拡大は不可避。通常インデックスも
`レコードサイズ 4->8` / `論理ブロックアドレス 3->6` / `開始オフセット 2->4` が要る。

**ただしインデックス密度が落ちる。C12（論理ブロックサイズ）と組み合わせて解決する。**

```
論理ブロック 1024B:  ヘッダ256 + フラグメント256 = 512 -> 残り  512 / 32 =  16 個（現 40 から悪化）
論理ブロック 4096B:  ヘッダ256 + フラグメント256 = 512 -> 残り 3584 / 32 = 112 個（現 40 より良い）
```

**A13 で 4KB を選んだことがここで効く。** `map_rec()` が 4KB 未満のブロックで使えない
制限とも整合し、**論理ブロック 4KB が自然な既定値**になる。

**③ フラグメントテーブル**: 拡張形式2 の 8 バイト形式を踏襲し `blk` を広げる

**④ システムヘッダ**: 最大ファイル数を 2->4 バイト（予約 12 バイトから捻出可能）

**⑤ ファイル所在データ**: 予約 4 バイトを使っても 2 バイト不足するが、
**192 バイト枠に入るので制約なし**（90 -> 92）

##### A2（`f_id` 32bit 化）の影響範囲

| 場所 | 現在 | 余裕 |
|---|---|---|
| ファイルIDテーブル | インデックス位置（暗黙）。エントリ 4 バイト = 開始ブロックアドレス 3 + 参照カウント 1 | — |
| **リンクインデックス** | 16 バイト構造の中 | **一番きつい（下記）** |
| ファイルヘッダのファイルID | 192 バイト構造の中 | 予約 16 バイトあり |
| リンクファイルのファイル所在データ | 90 バイト構造の中 | 不明 |

リンクインデックス 16 バイトの内訳を数えると:

```
 2 バイト  判別子（0x00, 0x80）＋ レコードタイプ
 ? バイト  レコードサブタイプ
 2 バイト  ファイルID
10 バイト  属性データ1〜5（UH × 5）
───────
14 バイト → 余り 2 バイト
```

**図70 を読んだ結果、余りはゼロだった**（サブタイプが 2 バイト占めている）。
`f_id` を 32bit 化するには**レコードインデックスの拡大が不可避**。上記 ② のとおり 32 バイトとする。

##### C3（`f_size` 64bit 化）— ファイルヘッダは拡大必須

拡張形式2 の `DfFileHeader` には `reserved1[8]` と `reserved2[8]` で **16 バイトの予約**がある。
しかし 64bit 化の増分を数えると:

```
size      4 -> 8    +4
nblk      4 -> 8    +4
ltime / atime / mtime / ctime  各 4 -> 8    +16
fid       2 -> 4    +2
                  ─────
                    +26 バイト      （nrec は 4 のまま。21 億レコードで十分）
```

**予約 16 バイトでは足りない。拡張形式3 ではファイルヘッダを 192 バイトから拡大する。**

幸い拡張形式2 で既に **`ridxofs`（レコードインデックス開始位置）が可変化**されている
（`(192+16) <= ridxofs <= 論理ブロックサイズ-16`）。この下限 `192+16` を新ヘッダサイズに
合わせて再定義すれば素直に拡張できる。**拡張の道が既に用意されていた。**

##### 判明した上限値

| 項目 | 幅 | 上限 |
|---|---|---|
| **開始ブロックアドレス**（ファイルIDテーブル） | **3 バイト** | 2^24 ブロック → 標準形式 1KB で **16GB**（C13） |
| **論理ブロックアドレス**（レコードインデックス） | **3 バイト** | 同じ（C13） |
| **参照カウント**（ファイルIDテーブル） | **1 バイト** | 255。拡張形式は 255 以上をファイルヘッダ `refcnt` に記録（**0 または 255 以上のみ。1〜254 は設定されない**） |
| **連続カウント**（レコードインデックス） | 1 バイト | 1 レコードの連続領域は最大 255 ブロック |

| ファイル所在データ | 90 バイト | リンクファイルでフラグメントテーブルの位置に入る。対象ファイルID / 対象ファイルの生成日時 / 対象ファイルシステム名 / 対象FSのデバイス所在名 |

##### 実装に必須の細部

**① ファイル短縮名のハッシュ（完全に規定されている）**

ファイル名によるファイル検索を高速化するためのテーブル（ファイルID 順、4 バイト × 最大ファイル数）。

```c
/* NAME[10] = ファイル名 40 バイトを 4 バイトずつパックした UW 配列（不足分は 0） */
短縮名 = 0;
for (i = 0; i < 10; i++) {
    短縮名 = 短縮名 ^ NAME[i];
    短縮名 を右に 1 ビット回転シフト;
}
```

**② データブロックの区切りコード**

論理ブロック内のレコード間の空き領域には、**先頭と最後に空き領域サイズ（2 バイト）を 2 つ**置く。

- 隙間なしなら値 0 の区切りコードが 2 つ連続
- 論理ブロックの先頭と最後の区切りコードは省略
- 隣接する空き領域は**常にマージ**され、2 つ以上連続して存在しない
- レコード操作では区切りコードを正しく再設定し、ブロック全体が空きになったら解放する

**③ レコードインデックスの配置規則**

- ヘッダブロック / インデックスブロック内でレコード順に並ぶ
- 途中（最初・最後含む）に任意個の未使用インデックスが入ってよい
- **接続インデックスは通常インデックスの直後から隙間なく連続**。論理ブロックの切れ目に
  未使用エントリが入ってはいけない
- インデックスブロックの未使用部分は全て未使用インデックスで埋める
- レコード挿入でインデックスブロックが溢れると**2 分割**して間接インデックスに登録

##### ルートファイル

- ファイルID = **0**
- ファイル名 = システムブロックのファイルシステム名と同一
- 参照カウント = **1**（決して削除できない）
- ファイル領域の先頭に必ず存在。フォーマット時に自動生成

##### 判明した重要な事実: μT-Kernel 3.0 の仕様にランデブは無い

「拡張同期・通信機能」に含まれるのは**ミューテックスとメッセージバッファだけ**で、
ポート／ランデブ（`cal_por` / `acp_por` / `fwd_por` / `rpl_rdv`）は仕様に存在しない。

実装 (`tron-forum/mtkernel_3`) には `kernel/tkernel/rendezvous.c` があるが、
`config/config_func.h` の `#define USE_RENDEZVOUS (1)` で切り替わる
**設定可能な実装拡張**であり、標準仕様の一部ではない。

**ただしこれは問題にならない。ランデブは BTRON3 仕様書自身の §1.3
「プロセス/タスク間同期通信管理」に完全なシグネチャで規定されている。**

```c
WERR cre_por(W maxcmsz, W maxrmsz, UW opt);
ERR  del_por(ID id);
WERR cal_por(ID id, UW calptn, VP msg, W cmsz, TMOUT tmo);
WERR acp_por(ID id, UW acpptn, W *rdv, VP msg, TMOUT tmo);
ERR  fwd_por(ID id, UW calptn, W rdv, VP msg, W cmsz);
ERR  rpl_rdv(W rdv, VP msg, W rmsz);
```

**したがって E1 / §3.5(c) の「BTRON3 §1.3 のランデブを拡張した同期 RPC」は、
正確には「BTRON3 §1.3 のランデブを拡張した同期 RPC」である。**
ランデブは周辺核のシステムコールとして BTRON3 が規定しており、
中心核の基準仕様を μT-Kernel 3.0 に切り替えたこととは独立している。

#### 詳細 D3 — SMP スケジューリング

**決定 (2026-10-11): グループ別に方式を分ける。**

##### 背景: なぜ仕様が沈黙しているか

マルチプロセッサ（SMP）自体は BTRON3 より古い（Burroughs B5000 1961 /
DEC VAX-11/782 1982 / Intel MP Spec 1994-97 / Windows NT 3.1 1993 /
Linux 2.0 1996）。しかし **1 チップに複数コアを載せるマルチコアは BTRON3(1999)・
B-right/V R4(2001) より後**である。

| 年 | |
|---|---|
| 2001 | IBM POWER4 — 最初の商用デュアルコア |
| 2005 | AMD Athlon 64 X2 / Intel Pentium D — コンシューマ機に到達 |
| 2006 | Intel Core 2 Duo で一般化 |
| 2011 | スマートフォンがデュアルコア化 |

2004〜2006 年頃に Dennard スケーリングが崩れてクロックが 3〜4GHz で頭打ちになり、
コアを増やす方向へ転換した。**BTRON3 は「来年の CPU は速くなる」が真だった時代の設計**で、
「絶対優先度グループ / ラウンドロビン群」は古典的なユニプロセッサ RTOS のスケジューラそのもの。
仕様の沈黙は見落としではなく時代。

##### 決定した方式

```
グループA（絶対優先度 0-127）= グローバルスケジューリング
   ランキュー 1 本。常に上位 N 個が走る。仕様の「厳密に優先度順」を守る
   システムプロセス・リアルタイムプロセスのみ = タスク数が少ないので
   ロック競合は実用上問題にならない

グループB/C（RR 128-255）= 半分割 + pull 型ロードバランシング
   コアごとのランキュー。アイドルコアが他コアから引き取る
   一般アプリ。キャッシュ親和性を優先
```

##### なぜ分けるか

絶対優先度グループは仕様で**「厳密に優先度順にスケジューリングされ」**と規定されている。
半分割にすると「コアAで優先度50、コアBで優先度100が走っていて、優先度30が
コアBのキューに並ぶ」という状態が起きえて、この規定に違反する。

**解決は仕様自身が示している:**

> 通常、**絶対優先度グループは、システムプロセスやリアルタイムプロセスに使用され、
> 一般のアプリケーションプロセスはラウンドロビングループ 1、または 2 を使用する**

**仕様が用途を分けているので、スケジューリング方式も分けられる。**
これは Linux の構造とほぼ同じ（`SCHED_FIFO`/`SCHED_RR` は実質グローバル、
`SCHED_OTHER` は per-CPU ランキュー + ロードバランシング）。

##### 群B/C の「相対的な実行頻度」の解釈

仕様は「優先度は相対的なスケジューリングの頻度を示す」とだけ書き、N コアでの意味を与えていない。

**決定: システム全体の CPU 時間に対する比率とする**（N コア合計を 100% とみなす）。
ユーザから見て「優先度 128 は優先度 160 の 2 倍走る」がコア数に依存せず成り立ち直感的。
Linux の重みベース配分も実質これ。

##### 方式の分類（参考）

| 方式 | 内容 | 評価 |
|---|---|---|
| グローバル | ランキュー 1 本。常に上位 N 個が走る | 仕様に最も忠実。ロック競合でスケールしない |
| パーティション | タスクをコアに固定。移動なし | キャッシュ効率最良。負荷が偏る |
| **半分割（pull 型）** | コアごとのランキュー ＋ アイドルコアが引き取る | **Linux / FreeBSD / Windows が全部これ** |

##### 本当の壁はスケジューリングではなくロック設計

I-right/V は単一 CPU 前提で、仕様書にこう書かれている。

> **ITRON 内部（クリティカルセクション内）を実行中に**ページフォルト例外や
> 一般保護例外などが**発生してはいけない**

単一 CPU では「割り込み禁止」がそのまま排他になるが、SMP では成立しない。
**中心核のランデブ、周辺核のファイルシステム、外殻サーバのすべてに実スピンロックが要る。**
これが SMP の本当のコスト。

**ただし E1 の決定が効く。** 外殻をサーバ群に分けたので各サーバは自分の状態だけを
ロックすればよく、巨大なカーネルロック 1 本にはならない。
マイクロカーネル構成は SMP と相性が良い。

##### ランデブの直接ハンドオフと SMP

E1 で決めた「同期 RPC の直接ハンドオフ」は単一 CPU 前提の最適化。
**SMP では「呼び出し側のコアでサーバを走らせる」のが自然な拡張**（QNX / L4 がやる形）。
キャッシュ的にも有利。詳細 E1 ④ の拡張項目 4 と一体で設計する。

#### 詳細 F1 — ドライバモデル

**決定 (2026-10-11): 原則ユーザランドドライバ。実現が困難な場合のみ例外的にカーネルドライバ。**

##### 仕様のインタフェースは配置によらず保てる

ITRON タスク + ランデブという形は、タスクがカーネル空間にいても別アドレス空間にいても
同じインタフェースで成立する。以下はすべて配置に依存せず維持できる。

- 属性データ（番号 < 0）/ 固有データ（番号 >= 0）の二分（F2）
- OPEN / CLOSE / CLOSEALL / READ / WRITE の通常要求
- ABORT / SUSPEND / RESUME / CARDEVENT / USBEVENT の特殊要求
- 要求種別ごとの `calptn` による選択受付
- 事象通知（メッセージバッファ）

##### カーネルドライバを認める基準

例外を無制限にすると原則が崩れるので、基準を明文化する。

| 基準 | 該当しうるもの |
|---|---|
| 割り込み応答レイテンシが厳しい | 高速シリアル、一部のリアルタイム I/O |
| カーネルのクリティカルパスにある | **タイマ / 割り込みコントローラ / MMU** |
| ブート時、ユーザランドが立ち上がる前に必要 | **初期シリアル / ブートディスク** |

これ以外は原則どおりユーザランドに置く。

#### 詳細 D8 — ブート方式と起動シーケンス（BV 調査結果）

**調査日 2026-10-11。**

##### ディスク構成 — MBR

```c
typedef struct {
    UB  BootInd;    UB  StartHead;  UB  StartSec;   UB  StartCyl;
    UB  SysInd;     UB  EndHead;    UB  EndSec;     UB  EndCyl;
    UW  StartBlock; /* 相対開始セクタ番号 (*) */
    UW  BlockCnt;   /* セクタ数 (*) */
} PartInfo;

typedef struct {
    UB       BootCode[446];
    PartInfo Part[4];
    UH       Sign;          /* 署名 = 0xAA55 */
} MasterBoot;
/* 2 バイト以上のデータはリトルエンディアン */
```

- ATA 仕様準拠。**CHS は無視し `StartBlock` / `BlockCnt` のみ使用**
- システムインジケータ（`SysInd`）が BTRON 区画を示す
- IDE ディスクは**常に 4 区画が登録**され、空区画のオープンは `ER_NOMDA`
- `Part[].StartBlock` はワード境界にならないので未アライメントアクセス注意（仕様が明記）
- MBR 読み書きは属性レコード番号 `-999999`、`magic = 'MBRR' / 'MBRW'`
- **CD-ROM は区画固定割当**: 1 = 全体 / 2 = ブートレコード（**El Torito** 2HD FD ブートイメージ）
  / 3 = BTRON ボリューム区画（BTRON 独自形式）

##### 設定ファイル `/SYS/DEVCONF`

```c
W GetDevConf(B *name, W val[L_DEVCONF_VAL]);     /* ワード値の配列を取得 */
W GetDevConfStr(B *name, B str[L_DEVCONF_STR]);  /* 文字列を取得 */
```

> デバイスコンフィグレーション情報は、`/SYS/DEVCONF` にファイルとして存在する。
> **このファイルは、システム起動時にメモリーに読み込まれる。**

項目名は最大 16 文字の ASCII。各ドライバがここから初期値を取る。実例:

| エントリ | 用途 |
|---|---|
| `VIDEOMODE mode [pmode] [w] [h] [pw] [ph]` | 表示モード番号と有効画面サイズ |
| `VIDEOVFREQ vfreq [p_vfreq]` | モニタ垂直同期周波数 |
| `VIDEOATTR attr` | `0x1` 仮想VRAM方式を強制 / `0x8` VESA BIOS のみ使用 |
| `RAMDISK バイトサイズ` | RAM ディスク（`mda`） |
| `FdChkPeriod` / `DiskChkPeriod` | メディアチェック周期（既定 0 / 3000 msec） |
| `FdSpec` / `HdSpec` | FD / HD 仕様 |

##### ファイル名前空間の起点

| パス | 役割 |
|---|---|
| `/SYS` | システムディスクの接続名 |
| `/SYS/DEVCONF` | デバイスコンフィグレーション情報 |
| **`/SYS/USR`** | **ユーザの作業環境（初期ウィンドウ）= 実行環境ファイル** |

##### ドライバの起動順序

- **カーネル組み込み形式**: `void XxxxxDriver(DevDrvParam *drvpar)` が初期起動タスクのエントリ
- **追加組み込み形式**: `ERR main(Bool StartUp, TC *arg)`。`[IMS]% kerext driver parameter` で起動

> **`main()` 関数から return しない限り次のデバイスドライバーの起動は行われない。**
> 起動順序に依存性がある場合は、return する前に必要な初期化処理をすべて終わらせておく
> ことで起動順序が守られる。

直列化を return のタイミングで表現している。宣言的ではないが確実。

##### ハードウェアリソースの事前登録

`hwresmgr` が起動時に PC/AT 固定の I/O マップを無条件登録する。

```
HW_IO(HW_SYSTEM) 0x0000-0x00FF
HW_IO(HW_IDE1)   0x01F0-0x01F7, 0x03F6
HW_IO(HW_VIDEO)  0x03B0-0x03BB, 0x03C0-0x03DF
HW_IO(HW_FDC)    0x03F0-0x03F5, 0x03F7
```

##### 起動モード選択とデバッグコンソール

ブート時に `[F8]` または `[CapsLock]`:

```
起動選択：［１］または［２］のキーを押してください。
    １．基本動作
    ２．通常動作
```

デバッグモードで **BMS / IMS** が有効になる。接続仕様:

| | |
|---|---|
| ポート | **COM1（I/O 0x3F8 固定）** |
| 速度 | 19200 bps / 8 ビット / ストップ 1 / パリティなし |
| フロー制御 | RTS/CTS |
| 文字コード | 日本語 EUC |
| 行末 | 送信 CR / 受信 CRLF |

BMS は RAM モニタで**論理アドレスで動作し、内部では全割り込みを禁止**する。
なお CLI は「コンソール小物」経由でデバッグモードでなくても使える。

##### 本OS での方針

| 論点 | BV | 本OS（推奨） |
|---|---|---|
| ブートローダ | MBR + BIOS | **UEFI**（x86_64 / arm64 共通）。MBR は読み取り互換のみ |
| 区画 | MBR 4 区画固定 | **GPT**。BTRON 区画の GUID を独自定義 |
| 設定 | `/SYS/DEVCONF` | **踏襲**（`GetDevConf` API も）。ただし ACPI / DT で自動検出できるものは書かない |
| ハードウェア列挙 | PC/AT 固定マップ | **ACPI (x86_64) / Device Tree (arm64)** |
| 起動時フレームバッファ | VESA BIOS | **UEFI GOP**。`VIDEOMODE` は上書き指定として残す（F6） |
| ドライバ起動順序 | `main()` の return で直列化 | 踏襲可。ただし**依存関係の明示宣言**のほうが素直 |
| デバッグコンソール | COM1 0x3F8 19200bps | シリアル（x86_64: 16550 / arm64: PL011 等）。**Phase 1 から必要** |
| 初期プロセス | 初期プロセス → 順次生成 | **仕様どおり** |
| 実行環境ファイル | `/SYS/USR` | **仕様どおり。**「システム立ち上げ時に最初にウィンドウを開くプロセスは必ず実行環境ファイルを設定しなければならない」 |

| E23 | **サーバの異常終了と復旧** | ★★ | 未着手 | E22 で 1 プロセス 1 サーバにしたことで意味を持つ問題。**WM が落ちると画面が全滅する。** サーバの再起動・状態復旧・クライアント側の再接続をどう設計するか。E12（`osta_prc`/`oend_prc` の契約がプロセス境界を跨ぐ）とも連動 |

#### 詳細 E1 — 外殻 11マネージャ + DP の分類

決め手は**呼び出し粒度**（IPC コストを決める）と**グローバル可変状態の有無**（信頼の必要性を決める）。

| マネージャ | 呼び出し粒度 | グローバル可変状態 | 代表 API |
|---|---|---|---|
| **DP** | **極細**（図形1個・文字1個ごと） | 無（描画環境はプロセス固有） | `gdra_lin` `gdra_str` `gfil_rec` `gcop_bmp` |
| **ウィンドウ** | 粗（開閉・移動）+ イベント毎 | **大**: ウィンドウ一覧・Z順・入力受付状態・親子木 | `wopn_wnd` `wget_evt` `wget_inf` |
| **メニュー** | 中（選択ループは対話的） | 小 ＋ **スクリーン全体へのポップアップと入力グラブを要求** | `mcre_men` `mopn_men` `msel_men` `mfnd_key` `mchg_atr` |
| **パーツ** | 細（ドラッグ中は毎イベント） | 無（`(wid, PAID)` のレジストリはプロセス固有） | `ccre_par` `cact_par` `cget_val` `cchg_par` |
| **パネル** | 粗 + 対話的 | 小 ＋ **パネルウィンドウ生成・フォーカス奪取・システムメッセージパネル（唯一）** | `pcre_pnl` `popn_pnl` `pact_pnl` `pget_gid` `pdsp_msg` |
| **トレー** | 粗 | **大**: プロセス間で共有するクリップボード | `topn_dat` `tget_dat` |
| **データ** | 細（読み出し中心） | **中: 最初から共有メモリ前提でプロセス間共用**（下記） | `dopn_dat` `dget_dtp` `ddef_dat` |
| **TIP** | 細（**1打鍵ごと + 変換中は全イベント**） | **中**: 学習辞書 | `iopn_tip` `iput_key` `ipup_sel` |
| **実身/仮身** | 中（+ プロセス間同期要求） | **最大**: アプリ登録・実行環境ファイル・FS接続・仮身状態 | `oexe_apg` `osta_prc` `oend_prc` `oreq_prc` |
| **フォント** | **極細**（DP が文字ごとに呼ぶ） | 中: 登録フォント一覧 + **巨大な読み出し専用グリフデータ** | `fget_img` `fget_inf` |
| **TCP/IP** | 中 | 大（元々サーバ的） | `so_socket` `so_select` |
| **印刷** | 粗 | 大（スプーラは元々別プロセス） | `pset_prc` `pprn_tad` |

ここから出てくる分割案:

**2026-10-11 改訂。** 各マネージャの API を精査した結果、初版の分類を 2 点修正した（下記 ①②）。

```
サーバ化（粗い呼び出し + グローバル状態）
  ウィンドウマネージャ   <- 入力配送をここで強制できる（E3 の解決）
  トレーマネージャ
  実身/仮身マネージャ
  印刷マネージャ         <- 元々スプーラ
  TCP/IPマネージャ

プロセス内ライブラリ（細かい呼び出し + 固有状態）
  DP                    <- ウィンドウごとのバックバッファが条件（E2）
  パーツマネージャ       <- 自ウィンドウの描画環境内で完結。修正不要

二分（ロジックはプロセス内、面と入力の占有は WM サーバ）   <- ② の修正
  メニューマネージャ     項目管理・状態・キー検索・選択ロジック / ポップアップ面＋入力グラブ
  パネルマネージャ       項目リスト・パネル内描画・モーダルロジック
                        / パネルウィンドウ生成・フォーカス奪取・システムメッセージパネル

中間（読み出し専用共有メモリ + 操作だけサーバ）
  フォントマネージャ     グリフデータは読み出し専用共有メモリ、登録操作だけサーバ
  データマネージャ       <- ① の修正。最初から共有メモリ前提の設計だった
  TIP                   変換エンジンはサーバ（1打鍵ごとの往復は人間のタイプ速度なら許容）
                        候補選択ポップアップは下記 ③ の面を使う
```

##### 4 つのマネージャが何を管理しているか

| マネージャ | 管理対象 |
|---|---|
| **パーツ** | ウィンドウ / パネルに登録された 11 種のコントロール部品。`(wid, PAID)` のレジストリ、各部品の矩形・値・属性（登録後変更不可）・状態（許可/禁止/不能/強調/枠/ドラッグ中断）、対話追跡ループ。11 種 = テキストボックス / シークレットテキストボックス / 数値ボックス / シリアルボックス / テキストオルタネート・モーメンタリスイッチ / ピクトグラムオルタネート・モーメンタリスイッチ / スイッチセレクタ / スクロールセレクタ / ボリューム |
| **メニュー** | メニュー項目リスト（メイン＋サブの 2 段、R4 で 3 段以上）、項目分類（状態項目=インジケータ付き / 動作項目 / 不能項目=灰色化 / 強調項目=下線）、キーマクロ文字、起点項目の記憶、標準メニューと汎用メニューの 2 系統 |
| **パネル** | ダイアログの項目リスト（`NULL` `PNTR` `PICT` `PATN` `BMAP` `ATXT` `TEXT` **`PART`** `ACTI` `FTXT`、さらに `VOB_PARTS`=仮身表示領域）、パネルの描画環境（`pget_gid`）、モーダルループ、エラーパネル、**システムメッセージパネル** |
| **データ** | **データボックス（リソースファイル）**。`(データタイプID, データ番号)` でリソースを引く。`PTR_DATA`(1) ポインタイメージ / `PICT_DATA`(2) ピクトグラム / `PAT_DATA`(3) パターン / `BMAP_DATA`(4) 図形ビットマップ / `FIG_DATA`(5) 図形セグメント / `TEXT_DATA`(6) 文字列 / **`PARTS_DATA`(7)** / **`MENU_DATA`(8)** / **`GMENU_DATA`(9)** / **`PANEL_DATA`(10)** / `USER_DATA`(64〜) |

**4 つはバラバラではない。** パーツ・メニュー・パネルの定義データはすべてデータボックスに入り、
`copn_par(wid, dnum, pos)` / `mopn_men(dnum)` / `popn_pnl(dnum, p)` がそこから生成する。
**データマネージャが 3 つのリソース供給元**という関係。

##### ① データマネージャは「中間」に属する（初版の誤り）

仕様の記述:

> 要求されたデータ項目が存在する場合は、そのデータ項目を**共有メモリ上**で参照できるように
> してそのメモリアドレスをアプリケーションに戻す。既に共有メモリ上で参照できる状態に
> あった場合は単にその領域のアドレスを戻す。**この場合は、複数のアプリケーション間で、
> そのデータ項目を共用していることになる。**

**最初から共有メモリ前提で、プロセス間でリソースを共用する設計だった。**
フォントマネージャと同じ構図なので「中間」に属する。

```
システムデータボックス        全アプリ共通・固定パス
アプリケーションデータボックス  アプリごと（通常はプログラムファイル内）
サーチ順: 後から開いたものが優先、システムは常に最後
   -> 同じ (型, 番号) でシステム既定をアプリ固有に上書きできる
```

##### ② メニューとパネルは二分する（初版の誤り）

両方とも**自ウィンドウの外に描き、入力を排他的に占有する**。

メニュー:
> メニューはポインタの下に表示され……メニューがスクリーンの上、下端にぶつかるような
> 場合は、**スクリーンの端にメニューの端が揃うように移動して表示される。**

パネル:
- パネルウィンドウは **WM が管理する特別なウィンドウタイプ**
  （「一般のアプリケーションが直接使用することはない」）
- **入力受付状態を主ウィンドウから横取りして占有**する
- システムメッセージパネルは**システム全体で唯一の資源**

| マネージャ | プロセス内 | WM サーバ |
|---|---|---|
| **メニュー** | 項目リスト管理 / 有効無効・インジケータ・強調 / キーショートカット検索 / 選択ロジック | **ポップアップ面の確保**（画面端の回避含む）/ **入力の排他グラブ** |
| **パネル** | 項目リスト / パネル内の描画 / パーツの配置 / モーダルロジック | **パネルウィンドウの生成** / **フォーカス奪取と復帰** / **システムメッセージパネル全体** |

##### ③ 帰結: WM サーバが提供すべき「面」は 3 種類

**メニューとパネルが必要としているのは同じ一つの能力**である。

> 「自ウィンドウの外に一時的な面を出し、その間の入力を排他的に受け取る」

WM サーバにこのプリミティブを 1 つ用意すれば両方が乗る。
Wayland の `xdg_popup` + grab と同じもの。

```
① 通常ウィンドウの面            （主 / 従属 / 前面）
② ポップアップ面 + 入力グラブ    <- メニュー・パネル・TIP 候補選択ポップアップが共用
③ システムメッセージパネル        （唯一・WM 専有）
```

**②で TIP も乗る。** R4 で追加された `ipup_sel()`（候補選択ポップアップ）が同じ能力を要求するので、
TIP を「中間」に分類したことと整合する。

この分割は現代のデスクトップスタックのプロセス境界とほぼ一致する
（Wayland コンポジタ / クライアント側描画 / プロセス内ツールキット /
freetype + 読み専 mmap / ibus・fcitx / CUPS / アプリレジストリ）。
同じ制約から同じ答えが出ていると見られる。

**DP をプロセス内に置く場合の問題**: DP の描画先は `BMP.baseaddr` という生ポインタで、
クリッピング(`GRGN`)は DP がソフトウェアで行う。DP がアプリのプロセス内に居ると、
アプリは `baseaddr` を直接書いてクリッピングを回避できる = ウィンドウの分離が「お願い」になる。
→ **ウィンドウごとのバックバッファ**（E2）で解決する。壊せるのは自分のウィンドウの中だけになり、
クリッピングは安全性ではなく正しさの問題に格下げされる。`gopn_dev("SCREEN")` のみ特権化。

#### 詳細 C4 — 実身の回収と循環参照

**調査日: 2026-10-11。両仕様を横断して確認済み。**

##### 仕様側の答え: 自動 GC は存在せず、三段構えの手動回収

**第1段: 参照カウント + カスケード削除**（`odel_obj()`、BTRON3 §3.8.5）

> 削除可能であるのは、ファイルの参照カウント = 0 で、かつ、そのファイルを参照している
> 仮身が登録されていない場合となる。この条件は**ネストしたファイルに対しても適用される**。

削除すると、含まれるリンクが指すファイルも削除可能になれば連鎖削除する。
**循環は回収できない。**

**第2段: 「くず実身」のオンライン回収**（BTRON3 §3.8 ディスク状態パネル — **仕様本体の機能**）

> **くず実身は、参照する仮身が 1 つも存在しない状態の実身を意味する。**

> 「ディスク状態パネル」を表示して[ディスク整理]を指定することにより、
> 「ディスク整理」ウィンドウが開かれ、その内部に**くず実身が表示される**。
> このウィンドウによりくず実身の削除、回収が可能となる。

- ディスク状態パネルに「使用実身数」と並んで **「くず実身数」** が表示される
- 仮身操作メニューの項目18「ディスク整理の実行」がこれ
- **GC が UI 機能としてユーザに委ねられている**

回収の足場は `get_nlk()`（BTRON3 §1.6.8）:

```c
WERR get_nlk(LINK *lnk)   /* リンクの順次取得。戻値は参照カウント */
```
> 本システムコールにより、ファイルシステム上に存在する
> **すべてのファイル(参照カウント = 0 のファイルも含む)**へのリンクを取り出すことができる。

ファイルID の昇順に全実身を列挙する。到達不能になった実身も必ず見つけられる。

**第3段: 循環はオフラインの fsck 相当のみ**（BV 第6編 `fsrcv` ファイルシステム修復）

> **隠れくず実身(ループ屑実身)は削除せずに、通常のくず実身として回収します。
> 回収した実身は `TRASH` と言う名前の実身を作成し、その中にリンクを格納します。**

- FS を切断して実行（「指定デバイスがファイルシステムとして接続されているときは、
  切断し、処理後に再接続します」）
- **削除せず、`TRASH` 実身に繋ぎ直してユーザから見える場所に戻す**

##### 用語

| 用語 | 意味 | 検出手段 |
|---|---|---|
| **くず実身** | 参照する仮身が 1 つも存在しない実身 | 参照カウント=0 で検出可。オンラインで「ディスク整理」が回収 |
| **隠れくず実身 / ループ屑実身** | **循環参照に囚われたくず実身**。参照カウント>0 なので「くず」として検出されない | **オフラインの `fsrcv` のみ** |

##### `library/appl/gabage.h` は GC ではない

アプリ層の**遅延削除ヘルパ**。「削除は保存するまで確定しない」という undo セマンティクスの実装。

```c
VOID reggabage(LINK *lnk, W on)   /* 屑ファイルの登録／解除 */
VOID delgabage(void)              /* 登録済みをすべて odel_obj() で実削除 */
```

- 仮身の[削除]時に `reggabage(lnk, 1)` で登録 → 取り消しは `reggabage(lnk, 0)`
- 実身の更新（保存）時に `delgabage()` で実削除
- 最大 256 件、同一ファイルシステム限定
- **循環参照とは無関係**

##### 評価

循環参照は BTRON において**バグではなく正常な使い方**。BTRON3 自身が
「リンク(仮身)による任意のネットワーク状の参照関係」と謳っており、相互参照
（A の中に B の仮身、B の中に A の仮身）は自然に起きる。
**想定内の現象に対して参照カウント方式を選んだのが設計上の弱点。**

一方 `fsrcv` の「消さずに `TRASH` に繋ぎ直す」は、実身がユーザ文書であることを
考えると正しい。GC のバグでユーザのデータが消えるのは許容できない。
**この作法は踏襲すべき。**

弱いのは**オンラインで循環が放置される**点。長期運用でじわじわ埋まる。

##### 選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| 踏襲 | 参照カウント + 手動「ディスク整理」+ オフライン `fsrcv` | 仕様準拠だが循環がオンラインで放置される |
| **推奨** | 参照カウントは仕様どおり維持し、**オンライン増分マーク&スイープを追加**。検出した循環は削除せず `TRASH` 実身に繋ぎ直す | 仕様の API セマンティクスを保ちつつ穴を埋める |
| 置換 | 参照カウントを捨ててマーク&スイープのみ | **不可**。参照カウントは `DfFileHeader.refcnt` としてオンディスクにあり、`get_nlk()` の戻値としても API に露出している |

**3案目が選べないのが重要な制約。参照カウントは外せない。**

推奨案を採る場合の追加論点: **GC 中のクラッシュ耐性**。ファイルシステムは永続なので
マークフェーズ途中の電源断で整合性が壊れてはいけない。**C9（ジャーナリング）と
一緒に設計すべき。**

実装すべきもの:
- オンライン: 参照カウント維持 + 増分マーク&スイープ（循環検出）
- UI: 「ディスク整理」ウィンドウ（くず実身をユーザに見せる窓）— BTRON の作法として残す
- オフライン: `fsrcv` 相当の fsck（C9 と同時設計）

##### ④ IPC — 一般 OS が何を使っているか

**決定 (2026-10-11): BTRON3 §1.3 のランデブを拡張した同期 RPC ＋ 共有メモリ・ハンドル渡し。**

###### 実際に使われているもの

| OS / システム | 制御メッセージ | 大きなデータ |
|---|---|---|
| X11 | Unix ドメインソケット | **MIT-SHM 拡張**（後から追加。元はソケットで画像を流していた） |
| **Wayland** | Unix ドメインソケット | **`SCM_RIGHTS` による fd 渡し**（`wl_shm` / `linux-dmabuf`） |
| Android Binder | **カーネル内 IPC ドライバ**。同期トランザクション、**優先度の引き継ぎあり** | ashmem / dmabuf の fd 渡し |
| Windows | **ALPC**（ポートベース） | 一定サイズ超は**共有セクション** |
| **Mach (macOS)** | **Mach ポート**（ケーパビリティ。権利自体をメッセージで渡せる） | **out-of-line memory**（VM の copy-on-write）。サーフェスは IOSurface |
| **L4 系 (seL4)** | **同期 `Call` で直接コンテキストスイッチ**。数ワードはレジスタ、以降はスレッド毎 IPC バッファ | 共有メモリフレームを事前マップ。ケーパビリティで権限を渡す |
| **QNX Neutrino** | **`MsgSend()` が同期でサーバへ直接切替。サーバはクライアントの優先度を継承** | `MsgRead`/`MsgWrite` でサーバがクライアントのバッファを直接読み書き |
| Minix 3 | 同期・**固定長**メッセージ | 明示的な **grant**（特定範囲へのコピー許可） |
| **Fuchsia (Zircon)** | **channel ＋ ハンドル渡し**。`zx_channel_call` で同期 RPC | **VMO** のハンドルを渡して共有 |

###### 抽出されるパターン

| | パターン | 採用例 |
|---|---|---|
| ① | **同期 RPC ＋ 直接ハンドオフ**（呼び出し側のタイムスライスでサーバが即走る） | L4 / QNX / Binder / Mach / ALPC |
| ② | **優先度の継承・委譲**（優先度逆転を防ぐ） | QNX / Binder |
| ③ | **メッセージでハンドル（ケーパビリティ）を渡す** | Mach / Fuchsia / Wayland(fd) / seL4 / Binder |
| ④ | **小さいメッセージは IPC、大きいデータは共有メモリ** | **全員。例外なし** |
| ⑤ | 高頻度ストリームは共有リングバッファ | virtio / io_uring |

**④には例外がない。** X11 が後から MIT-SHM を足し、Wayland が最初から fd 渡しにし、
Mach が out-of-line memory を持ち、Fuchsia が VMO を持つ。全部同じ結論。

**反例も記録しておく:** Windows NT 4.0 は性能のためウィンドウマネージャと GDI を
カーネル内（`win32k.sys`）に移した。ただし現代の Windows は合成をユーザモードの DWM に
戻している。**ハードウェアの速度とコンポジタモデルの登場で計算が変わった**ということ。

###### 本OS の用途ごとの割り当て

| 用途 | 頻度 | ペイロード | 方式 |
|---|---|---|---|
| `wopn_wnd` / `wcls_wnd` / 実身仮身操作 | 低 | 小 | ① 同期 RPC |
| **`wget_evt`（イベント取得）** | **高** | 小 | ⑤ 共有リング または ① |
| **ウィンドウのバックバッファ（E2）** | 低 | **巨大** | ③＋④ 共有メモリ + ハンドル渡し |
| トレー | 低 | 大 | ④ |
| **フォントのグリフ** | 高 | 大（読み専） | ④ ← 仕様が既にそう |
| **データボックス** | 中 | 大（読み専） | ④ ← 仕様が既にそう |
| `oreq_prc`/`orsp_prc`（3者間、E13） | 低 | 小〜中 | ① ＋ **転送** |
| TIP の `iput_key` | 高（1打鍵） | 小 | ① |

###### BTRON3 §1.3 のランデブが既に①と転送を持っている

```c
WERR cal_por(ID id, UW calptn, VP msg, W cmsz, TMOUT tmo);  /* 呼び出して応答待ち */
WERR acp_por(ID id, UW acpptn, W *rdv, VP msg, TMOUT tmo);  /* 受け付け */
ERR  fwd_por(ID id, UW calptn, W rdv, VP msg, W cmsz);      /* 別ポートへ転送 */
ERR  rpl_rdv(W rdv, VP msg, W rmsz);                         /* 応答 */
```

- `cal_por` / `rpl_rdv` が ① 同期 RPC そのもの
- **`fwd_por()` は QNX の `MsgForward` / Mach の権利転送と同じ発想**で、
  `oreq_prc` -> 他プロセス -> `orsp_prc` の 3 者間要求（E13）にそのまま使える
- `calptn` / `acpptn` のパターンマッチで、1 ポートから要求種別ごとに選択受付できる
  （BV のデバイスドライバがこれを使っている）

偶然ではなく、**ランデブモデル自体が同期 RPC のために設計されている**から。

###### 必要な拡張（4点）

| | 拡張内容 | 参考 | 連動 |
|---|---|---|---|
| 1 | **アドレス空間を跨ぐ転送。** `msg` は呼び出し側の空間のポインタなので、核がコピーするか共有領域を介する | QNX `MsgRead`/`MsgWrite`、Minix の grant | §3.2 |
| 2 | **優先度の継承。** μITRON3.0 のランデブには規定がない。ただし **I-right/V は優先度継承セマフォ（`vcre_pis` 系）を既に追加している**ので同系譜の拡張として自然 | QNX / Binder | **D3** |
| 3 | **ハンドル渡し。** μITRON に概念がない。バックバッファや共有メモリ領域の権限を渡す仕組み | Fuchsia の VMO ハンドル、Wayland の fd | **E2** |
| 4 | **SMP 対応。** `cal_por` の直接ハンドオフは単一 CPU 前提の最適化 | seL4 のマルチコア版 | **D3** |

###### 残る確認事項

イベント配送（⑤）を共有リングにする場合、`wget_evt()` の意味論を保てるか要確認。
モード指定が `WAIT` / `NOWAIT` / `NOMSG` / `RAWEVT` / `DRGEVT` / `MSG` / `DSPEVT` と多く、
さらに `wugt_evt()` / `wugt_evt2()` でイベントを戻す機能がある（戻したイベントは
通常のイベントに優先して取り出され、プロセス内に閉じる）。

#### 詳細 J2 — ライセンス構成

**現状: リポジトリの `LICENSE` は GNU GPL v2。**

GPLv2 のまま外殻をプロセス内ライブラリにすると、**リンクする全アプリケーションが GPL になる**。
サードパーティ製やプロプライエタリなアプリが作れなくなる。

##### 境界ごとの波及

Linux の `COPYING` にある有名な注記（「通常のシステムコールによってカーネルサービスを使う
ユーザプログラムには著作権は及ばない。それは単にカーネルの通常の利用であり派生物には当たらない」）
を当てはめると:

| 境界 | 性質 | GPL の波及 |
|---|---|---|
| 周辺核のシステムコール | トラップ | 及ばない（通常利用） |
| 外殻の「拡張システムコール」（`int 129` 相当） | **これもトラップ** | 及ばない可能性が高い |
| **標準ライブラリ / アプリケーションライブラリ / 多国語ライブラリ** | **通常のリンク** | **及ぶ** |

**本当の露出はライブラリ側。** `b*.h` 群・`libwin.h`・`tlang.h` / `wtstring.h` などは
アプリが普通にリンクする。

##### 定石の構成

```
中心核 + 周辺核 + 外殻サーバ           : GPLv2（Linux と同じ）
アプリがリンクするライブラリ群          : LGPL または寛容ライセンス（MIT / BSD / Apache-2.0）
  標準ライブラリ / アプリケーションライブラリ / 多国語ライブラリ
+ Linux 式の注記（システムコール経由の利用は派生物ではない）
```

- ItIs 由来コードを中心核に使う場合、ItIs は MIT/X11 系なので GPL とも寛容系とも両立する。
  著作権表示の保持だけが義務（§1）
- **後からライセンスを変えるには全コントリビュータの同意が必要**なので、コードを書く前に決める
- **E1 と連動**: 外殻を独立プロセスにすると GPL 境界の問題がほぼ消える。
  セキュリティ（E3・D7）に加えてサーバ化を支持する理由がもう一つ増える

（法的助言ではなく実務上の整理。§1 と同じ扱い。）

#### 詳細 H2 — `machine.h` の定数

**決定 (2026-10-11)**

```c
/* TRON 仕様種別（μITRON3.0 標準ハンドブック。BV と共通） */
#define SPEC_TRON   0x0000
#define SPEC_ITRON  0x1000
#define SPEC_BTRON  0x2000
#define SPEC_CTRON  0x3000
#define SPEC_mITRON 0x5000
#define SPEC_mBTRON 0x6000
#define SPEC_MAGIC(n)   ((n) & 0xf000)
#define SPEC_VER(n)     ((n) & 0x0fff)

#define BTRON_SPEC  (SPEC_BTRON | 0x320)   /* BTRON Ver 3.20 */

/* 機種 ID */
#define PCAT        0x00000010   /* PC-AT 互換機（BV 既定義） */
#define MACH_X64PC  0x00000020   /* x86_64 汎用 PC (UEFI)      <- 新規 */
#define MACH_ARM64  0x00000040   /* arm64 汎用 (UEFI)          <- 新規 */

/* CPU ID */
#define CPU_TRON    0x00000001   /* BV 既定義 */
#define CPU_I386    0x00000010
#define CPU_V810    0x00001000
#define CPU_X64     0x00000020   /* x86-64      <- 新規 */
#define CPU_ARM64   0x00000040   /* AArch64     <- 新規 */

/* プラットフォーム属性（両アーキ共通） */
#define ALLOW_MISALIGN  1   /* 通常ロード/ストアは可 */
#define BIGENDIAN       0   /* 両方リトルエンディアン（A4） */
#define VIRTUAL_ADDRESS 1
#define USE_PIC_PID     1   /* ELF + 動的リンカ(D2) + ASLR(I3) のため */
#define USE_ROM_MODULE  0
#define POWER_SAVE      1
```

##### 注意点

**① `BTRON_SPEC` の値の食い違い。** BV は `SPEC_BTRON | 0x302`（Ver 3.02）と宣言しているが、
準拠対象の仕様書は **Ver 3.20.00**。仕様書に合わせて `0x320` を選ぶ。**意図的な選択**。

**② R2 との緊張。** `machine.h` はコンパイル時のプラットフォーム情報だが、
R2 で「ページサイズは HAL が公開する値を参照」と決めた。
**`machine.h` にページサイズを定数として置いてはいけない。**
アーキが取りうる granule の選択肢を書くに留め、実値は実行時に HAL から取る。

##### D1 の CPU タイプ割り当て（実行プログラムレコードのサブタイプ）

既存:

```
0x100〜0x13F  TRONCHIP系    0x00 TRONCHIP32
0x140〜0x14F  68000系       0x40 68000 / 0x41 68010 / 0x42 68020
0x150〜0x15F  NS32000系     0x50 32032
```

##### コーディング規約

**修飾型（BTRON3 第1編 第1章の規定をそのまま使う）**

```c
#define CONST       const
#define LOCAL       static    /* モジュール(= 1ソースファイル)内でのみ使う変数・関数 */
#define EXPORT                /* 任意の箇所で参照可能な変数・関数の「定義」      */
                              /* 1個につきプログラム中に1箇所だけ記述           */
#define IMPORT      extern    /* 同じものの「参照宣言」                         */
#define VOID        void
```

**`EXPORT` / `IMPORT` の対が BTRON のスタイル。** 仕様書が
「モジュール = ソースファイル 1 個」と定義しているので翻訳単位の粒度も規定されている。

**関数名: `[prefix] 3文字 _ 3文字` の小文字**

| 層 | prefix | 例 |
|---|---|---|
| 周辺核 | なし | `cre_prc` `opn_fil` `get_evt` `wai_sem` |
| DP | `g` | `gdra_lin` `gset_chc` `gcop_bmp` |
| ウィンドウ | `w` | `wopn_wnd` `wget_evt` |
| メニュー | `m` | `mcre_men` `msel_men` |
| パーツ | `c` | `ccre_par` `cact_par` |
| パネル | `p` | `popn_pnl` `pact_pnl` |
| トレー | `t` | `topn_dat` |
| データ | `d` | `dopn_dat` `dget_dtp` |
| TIP | `i` | `iopn_tip` `iput_key` |
| 実身/仮身 | `o` | `oexe_apg` `osta_prc` |
| フォント | `f` | `fget_img` |
| TCP/IP | `so_` | `so_socket` `so_select` |

**型名: 全て大文字。分類 prefix + `_`**

`LINK` `RECT` `PNT` `SIZE` `EVENT` `MESSAGE` /

##### Phase 1 で判明したこと

**① L0 インデックス幅がアーキで違う（arm64 の実装上の罠）**

x86_64 の PML4 インデックスは bits[47:39] の 9 ビットで、1 本の木の
上位半分が 256..511 を使う。arm64 は TTBR0 / TTBR1 で木が分かれるため、
**上位半分も自分の木の 0 番から始まる**。さらに T0SZ=T1SZ=17 だと
L0 のインデックス幅は **8 ビット（256 エントリ）**になる。

9 ビットで取ると上位半分（bit47=1）で 256 以上になり、
表を飛び出してレベル 1 の変換フォルトになる。
**§3.2-2 で「アドレスの基底を揃えた」ことは、インデックス計算までは揃えない。**

**② 直接マップはページテーブル自身を含まなければならない**

MMU 有効化後、ページウォークはテーブルを直接マップ経由で読む。
早期プール（ページテーブルの置き場）が直接マップに無いと、
最初のウォークで変換フォルトになる。

**③ 例外ベクタを先に入れること**

上記 ①② はどちらも最初は**無言のハング**として現れ、原因が分からなかった。
`VBAR_EL1` を設定して ESR / FAR / ELR を出すようにしたら即座に特定できた。
**ベクタは MMU より先に入れる。**

**④ カーネルを上位半分へ移した（解消済み）**

当初カーネルがリンクアドレス（物理そのまま、低位）で走っていたため、
`hal_vm_switch()` で TTBR0 を差し替えると実行中の PC が無効になっていた。
足場 `hal_vm_identity_kernel()` で逃げ道を張っていたが、**カーネルを
`BTRON_KERNEL_BASE` (0xFFFF_FF00_0000_0000) にリンクし、起動を 2 段に
分けることで解消した**。足場は削除した。

```
ENTRY(_start_phys)                     ELF のエントリは _start の物理アドレス
KERNEL_VMA = 0xFFFFFF0000000000        リンク先（実行時アドレス）
KERNEL_LMA = 0x40080000                QEMU がロードする物理アドレス
各セクションに AT(ADDR(.x) - KERNEL_VMA + KERNEL_LMA)

第1段 boot_early()  物理で走る。コンソール・例外ベクタ・ページテーブルを
                    用意し MMU を有効にして戻る（恒等写像が残っている）
   start.S が ldr =__boot_stack_top / ldr =boot_main で VMA へ br
第2段 boot_main()   上位半分で走る。UART を MMIO 区画の別名へ、
                    例外ベクタを張り直し、hal_vm_drop_identity() で
                    TTBR0 を空の表へ向ける。以後 TTBR0 はプロセスのもの
```

**⑤ 物理で走っている間、C から取ったシンボルのアドレスは VMA ではない**

④ の実装で一番はまったのがこれ。clang はシンボルのアドレスを
`adrp`/`add` で求める。**`adrp` は PC 相対**なので、

| 実行段 | `(UD)&__kernel_end` が返す値 |
|---|---|
| 第1段（物理で走っている） | **物理アドレス** 0x4009_5000 |
| 第2段（上位半分で走っている） | **VMA** 0xFFFF_FF00_0001_5000 |

つまり**同じ C の式が段によって違う意味になる**。第1段で
`hal_kva_to_pa(&__kernel_end)` を呼ぶと二重にずれて 0x1_0080_1150_00 のような
あり得ない値になり、そこへの書き込みが**外部アボート**（その物理アドレスに
何も無い）になった。

対処として次の 2 点を規律化した（規律 **R17**）。

- **基準アドレス**はリンカスクリプトが `.rodata` 内に **値として**置いた
  `__kernel_vma_base` / `__kernel_lma_base` を読む。
  絶対シンボル（`__x = KERNEL_LMA;`）にすると、コンパイラがそのアドレスを
  `adrp` で求めようとして **±4GB の射程を外れ、リンクエラーになる**
  （`relocation R_AARCH64_ADR_PREL_PG_HI21 out of range`）。
  データとして置けば、イメージ内なので射程に入り、値は段によらず正しい。
- **大きさ**はシンボルの差分 `&__kernel_end - &__kernel_start` で取る。
  差分は段によらず一定。これと基準から `hal_kernel_pa_base/end()` を作り、
  第1段はこれだけを使う。

**⑥ 例外ベクタは上位半分へ移った後に張り直す**

第1段で設定した `VBAR_EL1` は `btron_vectors` の**物理アドレス**を指している。
恒等写像を捨てた瞬間に、例外が起きたらベクタに届かなくなる。
第2段で `hal_exception_init()` を呼び直す（そこでは `adrp` が VMA を返す）。

**⑦ アボートの原因は FSC まで出す**

③ の延長。`ESR_EL1.ISS` の下位 6bit (DFSC/IFSC) を分類して出すようにした。
**変換フォルト（写像が無い）/ アクセスフラグ / 権限フォルト /
外部アボート（その物理アドレスに何も無い）/ アドレスサイズフォルト**は
原因が全く違うので、EC だけ見ていると ⑤ のような
「アドレス計算そのものが壊れている」類を見落とす。

**注記:** `-kernel` で ELF を直接起動した場合、QEMU は x0 に DTB アドレスを
渡してこない（`DTB : なし`）。D8 で決めた UEFI 経由なら UEFI の
コンフィグレーションテーブルから DTB / ACPI を得られるので、
ハードウェア列挙は UEFI 対応後に行う。

検証済みの開発環境（`nix develop`）:

```
host     aarch64-darwin
clang    21.1.8    x86_64-unknown-none-elf / aarch64-unknown-none-elf の両方を生成
lld      21.1.8
qemu     11.1.1    hvf アクセラレーション利用可
UEFI fw  arm64 は pkgs.OVMF.fd から無料で入手 (FV/QEMU_EFI.fd)
         x86_64 は edk2 のクロスビルドが必要 -> nix build .#ovmf-x64 で opt-in
```
