# T2-17 入力装置ドライバ (virtio-input)

- **状態**: 完了（キーボード + 絶対座標 PD。枠は Device Tree から (R19)）
- **委譲**: ✗

- 依存: §1.7 イベント管理・§1.8 デバイス管理・GIC (T1-01)・FDT (D8)
- 触った: `include/btron/virtio.h` ＋ `src/drivers/virtio/mmio.c`（トランスポート）
  ＋ `src/drivers/virtio/input.c`（装置）＋ `include/btron/machdesc.h` と
  `src/kernel/boot/fdt.c`（virtio-mmio の枠）＋ `hal_dma_barrier`
- 実装: virtio-mmio Version 2 ＋ split virtqueue ＋ virtio-input
  （キーボード / 絶対座標 PD / 相対座標 PD）

**なぜ virtio-mmio か。** arm64 の QEMU virt 機種には PS/2 が無い。
PCIe は列挙と割込み経路（INTx の _PRT か MSI-X の ITS）が要り、USB は
もっと重い。virtio-mmio は枠が Device Tree に全部書いてあり、割込みも
普通の SPI なので、**アドレスも割込みも記述から取れる（規律 R19）**。

**キートップコードは evdev のキーコードをそのまま使うと決めた。**
仕様 §1.7.3 は「キーボードにより規定される」として値を定めていない。
evdev のコードは元々「キーの物理的位置」の番号で意味が一致し、0〜255 に
収まって `KEYMAX` = 256 と合う。`KeyTab` は「evdev コード → TRON 文字
コード」の表になる。

**役割の分け方。** 配列を知っているのはドライバだけなので、
「どのキートップがシフトか」はドライバが決め (`evt_meta`)、
文字コードへのエンコード・キュー・自動リピート・ボタン状態は周辺核が
持つ (`evt_key` / `evt_pd_*`)。

- **既知の制限**
  - 旧式インタフェース（MMIO Version 1）は扱わない。QEMU は既定で
    旧式を出すので `-global virtio-mmio.force-legacy=false` が要る
    （`run_qemu.py --input` が面倒を見る）
  - ACPI 経路では枠の記述が DSDT の AML の中にあり読めない → T1-15
- **受入条件**（すべて通過）
  - ctest の `input-arm64` 構成で「入力枠 2 台」＝「入力装置 2 台」
    （見つけた台数と動かせた台数が一致すること）
  - キーボードが `"kbd"`、PD が `"pd"` でデバイス管理に出ること
  - 既定の変換表で evdev 30 番が `'a'`、左シフトで `'A'`、
    命令シフトで `0x01` になること
  - **マスクで消されてもキー状態配列は更新される**こと
  - 絶対動作タイプでは `set_pdp` が `ER_OBJ` を返すこと
