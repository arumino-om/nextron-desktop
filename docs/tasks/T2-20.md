# T2-20 cre_prc と実行プログラムレコード

- **状態**: 完了（実身の先頭レコードから読み込んで EL0 で起動）
- **委譲**: ✗

- 依存: T2-18 ファイル管理・T2-19 EL0
- 触った: `include/btron/objfmt.h` ＋ `src/kernel/periph/exec.c`
  ＋ `proc.c` の `cre_prc` ＋ `tools/mkobj.py` ＋ `src/user/`

仕様 §1.1.6「指定したファイル内の**最初の**実行プログラムレコードの
内容が生成するプロセスのプログラムコードとなる。実行プログラムレコードは、
**先頭レコードでなければならない**」。共有データ仕様 3.2 でレコード
タイプ 9、サブタイプが CPU のタイプ。

**オブジェクト形式は本OS が決めた。** サブタイプ（CPU タイプ）の表は
仕様にあるが、形式そのものの中身は手元の仕様書にない（§5 未読箇所）。
64 ビットの CPU が表に無いので **A17** として拡張した
（x86-64 = 0x64、AArch64 = 0x80）。

**確保したページは自分で覚えて返す。** `hal_vm_destroy` はページ
テーブルしか返さない（葉が指すデータページは写像した側の持ち物、
という規律 R18 の約束）。忘れるとプロセスごとに像の分だけ失う。

- **受入条件**（すべて通過）
  - 実身に書いた実行プログラムレコードから EL0 のプロセスが起きる
  - 起動メッセージがユーザ空間まで届く（仕様 §1.1.6 の形式-A）
  - 終了コードが親へ届く
  - 先頭レコードでない／タイプが違う／サブタイプが違う／ヘッダの
    CPU が違う／印が壊れている、のいずれも `ER_REC`
  - 像のページがプロセス終了で返る
