**なぜ要るか。** ここまで、ドライバの登録もファイルシステムの接続も
**検査コードの中**で行っていた。つまり「電源を入れると OS が立ち上がる」
経路が存在せず、検査が全部を駆動していた。ファイルシステムも RAM
ディスクの上にしか無いので電源を切ると消える。

## やったこと

| | |
|---|---|
| virtio-blk ドライバ | 論理デバイス名 `"vda"`。**サブユニットが GPT の区画**になる |
| GPT の区画表 | LBA1 のヘッダと区画エントリを自分で読む。バイト位置を明示（規律 R1） |
| BTRON 区画の判別 | タイプ GUID（詳細 D8 / `tools/mkimage.py` と同じ値）で見分ける |
| 起動列 `sys_startup()` | ドライバ登録 → ディスク発見 → 接続（未構築なら構築）→ 実行プログラムの配置 |
| ディスクイメージ | `mkimage.py` が**区画 2（BTRON 区画）を空のまま**作る |
| `\BTRON\SELFBOOT` の印 | この印があるとカーネルは起動時検査の代わりに起動列を通す |
| 永続性の検査 | `run_selfboot.py` が**同じイメージで 2 度起動**する |

**ディスクは選ばなくてよい。** UEFI 経路では QEMU に起動ディスクを渡して
いて、ファームウェアが起動に使っているその同じディスクが virtio-blk として
見えている。つまりカーネルは自分が入っているディスクを読み書きできる。

**構築してよい区画は GPT のタイプ GUID で分かる区画だけ。** 中身が本OS の
形式でなければ `att_fls` が `ER_TRON` を返すので、それを「まだ構築して
いない」と解釈して 1 度だけ構築する。他の OS の区画は触らない。

**パス名でたどるには仮身が要る。** `cre_fil` は実身を作ってリンクを返す
だけで、親からたどれるようにはしない。仕様 §1.6.1 のとおりディレクトリは
存在せず、参照関係は「ファイルの中のリンクレコード」が作るので、
ルートに仮身を置く（`sys_put_link`）。これを忘れると
`get_lnk("／sys／shell")` が `ER_NOEXS` になる（実際に踏んだ）。

## 判明したこと

**`-drive if=virtio` は arm64 virt では virtio-blk-pci になる。** virt 機種
には PCIe ホストブリッジがあり、既定の virtio バスは PCI である。本OS の
virtio は mmio トランスポートしか持たないので、カーネルからは見えなかった
（「永続する記憶装置がありません」と出て原因が分からなかった）。
`-device virtio-blk-device` が mmio 版で、入力装置を
`virtio-keyboard-device` で挿しているのと同じ理由である。
**ファームウェアは mmio のディスクからでも起動できる。**

**割込みは使わない。** 要求を出してから結果が要るまでの間に他にやることが
無い（ファイル管理が同期的に呼ぶ）ので used リングを見張る。avail リングに
`VQ_AVAIL_F_NO_INTERRUPT` を立て、GIC 側も有効にしない。ハンドラの無い
割込みが上がり続けると EOI だけ出して回り続ける（`intc_dispatch`）ので、
上げさせないのが一番安全。

**ドライバの登録は 2 度呼ばれる。** 起動列と検査の両方から呼ばれるのに、
デバイス管理は同名の二重登録を弾かない（同じ名前の 2 つのユニットが
できて名前引きが壊れる）。各ドライバ側で 1 度しか登録しないようにした。

## 受入条件（すべて通過。`selfboot-arm64`）

- ディスクが見つかり、GPT の区画が 2 件、BTRON 区画が分かること
- **1 回目**: 未構築 → 構築 → 実行プログラムと印を置く
- **2 回目（同じイメージ）**: 「既に構築済み」になり、
  **前回置いた印の中身が読めること**
- **ディスク上の実行プログラムから外殻が起きること**（埋め込みではなく
  実身から読む）。EL0 で動き、正常終了すること
- 既存の 9 構成が 174/174 のまま通り続けること

## 残り

- `/SYS/DEVCONF`（装置構成ファイル）の**書式と意味論**は仕様原文が要る。
  論点として `design-issues.md` §4 の D8 に差し戻した
- 実行環境ファイル (`/SYS/USR`) と起動時のユーザ環境の決め方（同じ）
- 起動列から**外殻を常駐させて居座る**経路。いまは検査が終わると
  `hal_exit()` する（`HOLD` の印があるときだけ居座る）。
  本来は「初期プロセスが外殻を起こして待つ」形にする
- ブロックデバイスのキャッシュ。いまは 1 要求ごとにディスクへ行く
- 書き込みの途中で電源が落ちたときの耐性（C9 ジャーナリング）
