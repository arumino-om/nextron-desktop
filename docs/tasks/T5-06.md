# T5-06 ウィンドウごとのバックバッファと合成 (E2)

- **状態**: 完了（アプリは裏画面へ描き、マネージャが合成する。ポインタはレイヤ）
- **委譲**: ✗

- 依存: T5-05・T4-12・T4-11
- 設計: **詳細 E2**（docs/design-issues.md）
- 触った: `include/btron/dp.h`（`PtrShared` / `gptr_paint`）＋
  `include/btron/winmsg.h`（`WinEnv` に裏画面）＋
  `src/subsystems/window/winman.c`（確保・合成）＋
  `src/lib/appl/window/wincli.c`（描画先の差し替え）＋
  `src/lib/dp/pointer.c`（レイヤ化）＋ `demo.c` / `shell.c`

**アプリは画面ではなく自分の裏画面へ描き、マネージャが合成する。**
直描きで順に出た 3 つの不具合（ポインタの書き残し / ちらつき /
裏の枠が消える）は、どれも「描き手が複数いて、誰が何を描き直すかの
申し合わせが要る」ことから来ていた。合成にすると申し合わせが消える。

段取りは設計どおり 4 段。

1. **窓ごとのビットマップ。** 共有メモリ (`M_COMMON | M_RESIDENT`)。
   上位半分は全プロセス共通なので番地をそのまま `WinEnv` で渡せる。
   見方を 2 つ開く —— `bgid` は画面の絶対座標でそのまま描ける（枠を
   描くのに使う）、`gid` は相対 (0,0) が作業領域の左上（アプリ用）
2. **損傷矩形の合成。** 机 → 奥から手前へ窓、の順。机を塗るのは
   ウィンドウが無い所だけ（前置長方形リストで外す）。要求を 1 つ
   配り終えるたびに `win_flush` が走る
3. **ポインタをレイヤにした。** save-under を捨てた。下地は合成で
   作り直せるので退避する理由が無い。`PtrShared` は位置・形・消去
   要求数だけになり、16KB の退避面が消えた。追従を回すのも
   マネージャの仕事になった
4. **前置長方形リストは空。** 自分のビットマップに手前も奥も無い。
   `gset_for` / `gget_for` の API は仕様どおり残っている

**踏んだ落とし穴: 変形で裏画面を取り直すと落ちる。** 利用側は別の
プロセスで、取り直した瞬間に古い番地へ描いていると解放済みの共有
メモリを踏む（`dp_run` で変換フォルト）。**画面 1 枚分を確保して
ウィンドウの寿命に合わせる**ことで、番地が動かないようにした。
1.9MB × 16 枚で 30MB、実測 485MB の管理下に収まる。

- **既知の制限**
  - **分離にはなっていない。** 共有メモリは全プロセスから書けるので、
    他のアプリの窓を壊せる。E2 が元々狙っていた分離にはハンドル渡し
    （詳細 E1 ④ / 規律 R10）が要る。得たのは正しさであって安全性ではない
  - **損傷の通知が無い。** アプリは好きなときに自分の裏画面へ描くので、
    どこが変わったか分からない。要求のたびに窓を貼り直している
    （机は触らない）。QEMU で 1 回 3ms 程度
  - ドラッグ中はサーバがその中で回るので合成も止まる（T5-04 の制限と同じ）
  - **E23 が悪化した。** WM が落ちると窓のビットマップごと消える
- **受入条件**（すべて通過）
  - 別のプロセスに塗らせても、裏のウィンドウの枠が戻る
  - ポインタがマネージャの合成で画面に出る / 消すと下地が出る
  - §2.6.2 の 4 通り（前景 / 背景 / 透明 / 反転）が合成でも出る
  - 重なった窓を変形しても落ちない（番地が動かない）
