## 何が起きていたか

画面が激しくちらついていた。原因は 2 つあって、**どちらも「画素を何回
書くか」ではなく「途中の状態が見えるか」の問題**だった。

**① 要求のたびに全ウィンドウを貼り直していた。** E2 で裏画面を入れた
とき、「利用側がどこを描いたかを知る手立てが無い」ので、マネージャは
要求を 1 つ配るたびに全部の窓を画面へ貼り直していた（`win_flush` の
`all_frames` の経路）。アプリは 10ms ごとにイベントを問い合わせるので、
**何も変わっていなくても画面が書き換わり続ける**。走査がその途中を
拾うと、窓の中身が裂けて見える。

**② 合成を画面へ直に組んでいた。** 机を塗る → 窓を奥から貼る →
ポインタを載せる、の 3 段階が画面上で起きるので、走査が段の途中を
拾うと下地やポインタの消えた瞬間が見える。ポインタを動かし続けると
これが連続して起きる。

## 直し方

**① 損傷の通知**（詳細 E2 が宿題として残していた分）

描画環境に「変わった範囲」の置き場を登録できるようにした
（`gset_dmg` / `DMGREC`。**本OS の拡張で、仕様の API は 1 つも
変わらない**）。マネージャは窓ごとの記録を**共有メモリ**に置き、
その番地を `WinEnv` で利用側へ渡す。利用側のディスプレイプリミティブは
裏画面へ描くたびに範囲を積み、マネージャは**積まれた所だけ**貼り直す。
何も積まれず、ポインタも動いていなければ**画面を 1 画素も触らない**。

記録は**区間単位**で積む（画素ごとではない）。走査線の速い経路
（T4-11）を台無しにしないため、`dp_run` / `dp_copy_run` / `dp_plot` の
3 か所にだけ入れてある。

**② 一時面での合成**

画面と同じ大きさの一時面を 1 枚持ち、机・窓・ポインタをそこへ組んでから
**損傷の矩形を 1 回だけ**画面へ転送する。画面の各画素は更新ごとに
ちょうど 1 度しか書かれないので、途中の状態が見えない。
ポインタも一時面へ描けるようにした (`gptr_paint_to`)。
一時面が取れない構成では画面へ直に組む（ちらつくが動く）。

## 判明したこと

**座標系が 2 つある。** 裏画面のビットマップは画面と同じ大きさだが、
**列 0 は窓の外枠の左上**に対応する（`setup_gid` の「絶対 = 相対 -
bounds.left」）。利用側が積む損傷はこのビットマップ座標なので、
マネージャは外枠の位置を足してから画面座標として扱う。最初これを
忘れて、窓の一部だけが更新されない状態になった。

**「毎回貼り直す」は抜けを隠していた。** 損傷だけを貼るようにした
とたん、描き直したのに損傷を積んでいない箇所が画面に出た（入力受付
状態の移動・ウィンドウの生成・タイトルの差し替え・作業領域の消去の
4 か所）。**貼り直しで隠れていた不整合が、効率化で表に出た**形で、
5 か所に `damage()` を足して直した。

**受け渡しに競合がある。** 積む側（利用側のプロセス）と取る側
（マネージャ）が同じ記録を触るのに、原子的な交換が無い。「読む →
消す」の間に積まれた分を取りこぼすと、画面だけが古いまま残る。
連番を前後で見て、変わっていたら**窓全体を損傷とみなす**ことで閉じた
（保守的に広く貼るだけなので正しさは失われない）。

## 受入条件（すべて通過）

- `ctest --preset arm64` が 11 構成すべて通ること（検査 174 件 + 自立起動）
- 何も変わっていないとき、画面への書き込みが 0 であること
  （`win_flush` が合成を呼ばない）
- 入力（ポインタ移動・キー入力・点描き）が従来どおり画面に出ること
  — 入力を流し込んだスクリーンショットで確認
- 一時面が取れない構成でも動くこと（画面へ直に組む経路を残した）
- 全構成の検査を 2 回続けて通すこと（取りこぼしは時々しか出ないため）

## 残り

- **アプリが描いた直後に要求を出さないと画面に出ない。** いまは要求を
  配り終えた時点で合成するので、描いたまま何も要求しないアプリの絵は
  次の要求まで出ない。実害は出ていない（イベントを取るか再表示を
  確かめるかで必ず要求が出る）が、明示的な「描いた」通知があると素直
- 損傷の矩形は窓ごとに 1 つの外接矩形。離れた 2 か所を描くと間も貼り直す
- 一時面は画面 1 枚分の共有メモリを使う（1280x800 で 4MB）
