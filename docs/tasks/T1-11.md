## 判明したこと

**① 位置独立に作らないと起動第 1 段が動かない（規律 R30）。**
§3.2-3 の `BTRON_KERNEL_BASE` は `0xFFFFFF00_00000000` で、x86_64 の
`-mcmodel=kernel` が前提とする「上位 2GB」には入らない。既定の small
モデルはデータ参照を 32bit の符号付き絶対値で組むのでリンクが
`R_X86_64_32S out of range` で落ちる。**large モデルにすると今度は関数
呼び出しが movabs + 間接 call になり、物理アドレスで走っている第 1 段が
上位半分へ飛んでページフォルトする。** `-fpie` で参照を RIP 相対にすると、
同じ像が物理でも上位半分でも動く（arm64 が adrp/add で自然にそうなって
いる性質を、x86_64 では明示的に買う）。`-mno-red-zone` も要る。

**② UEFI の GDT は使い続けられない。** CR3 を自前の表に差し替えると
ファームウェアのメモリが写像から外れる。GDT は普段 CPU の中にあるので
一見動くが、**割込みや例外でゲートの CS を読むときに GDT を引く**ので、
そこでページフォルト → ダブルフォルト → トリプルフォルトになる。
症状は「出力が途中で止まり QEMU が黙って終わる」で、例外の報告すら
出ない。カーネルのメモリに GDT を置き、起動の両段で張り直す。

**③ 直接マップは RAM 全部に張らなければならない。** 最初はカーネルと
早期プールだけを張っていたが、物理ページアロケータが配ったページを
ゼロクリアするのに直接マップ経由で触るので、画面を立てるときの
ページテーブル確保で「写像が無い」ページフォルトになった。arm64 側は
既にそうなっていた（Phase 2 ㉛）ので、同じ形に揃えた。

**④ 物理 0 番地を配ると「成功」と「失敗」が区別できない。**
`pmem_alloc()` は失敗を 0 で返す契約なのに、x86_64 では 0 番地が表の
内側に来る。さらに野良の `pmem_free(0, …)` が本物のページ（実際には
ページテーブル）を解放していた。**0 番地は配らない**ことにし、
あわせて「このアロケータが配る対象か」の表を持たせて、身に覚えのない
解放がファームウェアやカーネル自身の領域を空きに戻さないようにした。

**⑤ 256 本のベクタスタブをラベルで並べる書き方は通らない。**
`.altmacro` の `btron_vec_\n` 方式は LLVM の統合アセンブラで
「expected relocatable expression」になる。**16 バイト間隔に揃えて
「先頭 + 16 × ベクタ番号」で引く**形にした。

**⑥ QEMU の `-kernel` に x86_64 の ELF は渡せない。** Linux boot protocol を
期待されるので、x86_64 は UEFI 経由だけを支える（arm64 の直接起動に
相当する経路は作らない）。

## 2 段目で分かったこと（Local APIC）

**「どの割込みが起きたか」の聞き方が GIC と逆である。** GIC は `GICC_IAR` を
読むと INTID が返る（読んだことが受領になる）が、x86 は**ベクタごとに別の
ゲート**で、起きた後にレジスタへ聞く手段が無い。そこで**ゲートが受け取った
ベクタを 1 つだけ預ける**形にした（`apic_take_vector()`）。
`hal_intc_acknowledge()` が 1 度だけ返して空にし、2 度目は 1023 を返すので
`intc_dispatch()` のループが 1 周で終わる。

**tick の割込み番号の出どころがアーキで違う。** arm64 は generic timer の
PPI が記述 (GTDT / FDT) にあるが、x86 の Local APIC タイマは**番号を
ソフトウェアが選ぶ**。中心核が `MachDesc` を直に引いていたのをやめ、
`hal_timer_tick_intid()` を HAL の契約に足した（中心核は「HAL が使う番号」
だけを知る）。

**APIC タイマの周波数はどこにも書いていない。** `CNTFRQ_EL0` に当たるものが
無く、CPUID 0x15 は QEMU では 0 を返す。TSC（`timer.c` が PIT で較正済み）を
物差しにして「1ms の間にいくつ減ったか」で較正した。実測 1000MHz。

**2 回以上来たことが EOI が効いている証拠である。** EOI を出さないと APIC は
同じ優先度の割込みを 2 度目から上げない（ISR のビットが立ったまま）。
1 回で止まっていたら「来たが受領していない」で、そこを見分けられるのは
到来回数しかないので、検査は 3 回を要求し ctest も外から同じ行を要求する。

**`hal_intc_enable()` に当たるものが Local APIC には無い。** GIC の
`GICD_ISENABLER` に相当する表は無く、あるのはベクタごとの LVT（タイマ等）と
IOAPIC のリダイレクション表（レガシ割込み。F9 で後回し）だけである。
MSI は装置側が送るので受ける側に設定が要らない。嘘の失敗を返すと中心核が
止まるので、LVT タイマ以外は何もせず `E_OK` を返す。

## 3 段目で分かったこと（コンテキスト切替）

**戻り先がレジスタかスタックかで、フレームの形が変わる。** arm64 は x30
（リンクレジスタ）に戻り先が入るので、フレームに「x30 の退避」として置く。
x86_64 は `call` が戻り番地を**スタックに積む**ので、push/pop の列がそのまま
フレームになり、最後の `ret` がスタックから戻り先を取る。トランポリンへの
着地も、arm64 は「x30 に仕込んで ret」、x86_64 は「フレームの一番上に
仕込んで ret」になる。

**整列が ABI の要求と逆向きに効く。** ABI は `call` の直前に RSP が 16 の
倍数であることを要求する。トランポリンは `ret` で着地するので戻り番地が
積まれておらず、**着地時点の RSP が 16 の倍数**でなければならない。
フレームは 56 バイト（8 mod 16）なので、底を 8 mod 16 に置く
（`(top & ~0xF) - 56` がちょうどそれ）。ここを間違えると、clang が構造体の
複写で出す SSE 命令が一般保護例外になる。しかも揃っている経路では動くので、
症状が構造体の大きさに依存して現れる。

**フレームの大きさは HAL の外に出せない。** `HAL_CTX_FRAME_SIZE` が
`include/btron/hal.h` に 1 つだけあったが、arm64 は 0xA0（12 本 + 浮動小数点
8 本）、x86_64 は 56（6 本 + 戻り番地）で、レジスタの本数も戻り先の置き場も
違う。使うのは各アーキの `context.c` だけなので、そちらに移した。

**1GB ページは任意機能である。** 直接マップを大ページで張る (T6-03 / 判明
(66)) のを x86 にも入れたところ、arm64 には無い分岐が要った —— 1GB ページ
(PDPE1GB) は CPUID 0x8000_0001 EDX bit26 で任意機能で、無い機械で `PS` を
PDPT へ書くと**予約ビット違反のページフォルト**になる。無ければ 2MB から
始める。

**中心核の検査が x86 で初めて走り、2 件落ちた。** どちらも「検査が arm64 の
形で書かれていた」ことによるもので、実装の誤りではなかった。

- 「割込みとタイマ」が `hal_intc_version() == 2 || == 3`（GIC の版）を
  要求していた → アーキで分けた（x86 は xAPIC の 0x10 以上）
- 「直接マップは RAM 全域をブロックで覆う」が落ちた → **これは本物の
  不足**で、x86 の `map_direct` が 4KB 粒度だった。上記の大ページ化で直した

**周辺核以上は飛ばす。** 初期プロセスの検査は ring 3 まで降りるものを含み、
`hal_ctx_init_user` がまだスタブである。飛ばしたことを 1 行出す ——
数が合っているのに中身が違う状態を作らないため。
