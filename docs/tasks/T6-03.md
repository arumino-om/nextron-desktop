# T6-03 実機規模への耐性

- **状態**: **完了** — 32GB / 16 コアの構成を実際に作って通した
- **委譲**: ◎

- 依存: なし
- 参照: **詳細 F9** の「実機で初めて効く差」/ Phase 1 ⑩⑪ / Phase 2 ㉚㉛
- やること（どれも QEMU の既定では当たっているが実機で外れる）
  - RAM 16〜64GB — 直接マップを 4KB 粒度で張ると表が物理メモリの 1/512 に
    なり、早期プールに入らない。**ブロック記述子 (1GB / 2MB) で張る**。
    ページのビットマップも語単位にする
  - メモリマップの要素が 192 を超える場合の畳み方。**穴は跨がない**
    （一覧に出てこない物理アドレスは「空き」ではない）
  - **GOP の `PixelBitMask`**（`BFB_OTHER` は置いてあるが未対応）
  - 1920x1080 以上での描画時間
  - `MD_MAX_CPUS` を超える機械で切り捨てても数は数えること
- 検査区分の order: **762**（`registry.md` §2 の L11 帯）
- **受入条件**: 大容量メモリと多コアの構成を実際に作って通す。
  作れない構成（画素形式・メモリマップの畳み）は純粋な関数に切り出して検査する

## この土台へ移すときに変えたところ

- 判明を **(66)〜(68)** に付け替えた（T6-01 が (57)〜(61)、T6-02 が (62)〜(65)）
- **`page.c` は「語単位」と「配ってよい印 (`pm_ok`)」を両立させた。** レーンは
  古い `page.c` を基準にしていて `pm_ok` を知らず、そのまま取ると
  **野良の `pmem_free()` でカーネル自身の領域が空きに戻る**。語単位の操作を
  `ok_range()` として `pm_ok` 側にも用意し、両方の性質を残した
- `memmap.c` / `bootfb.c` は**ローダとカーネルの両方に結合する**。純粋な関数に
  してあるので、`cmake/uefi-loader.cmake` と `src/kernel/boot/sources.cmake` の
  両方へ足した（この土台はソース列挙がディレクトリごとに分かれている。W0-2）
- 検査は登録制の `src/kernel/core/tests/{mm,dp}.c` へ入れた（W0-1）
- `run_qemu.py` の `--memory` と T6-02 の `--no-semihosting` が同じ関数の
  引数で衝突したので、両方を受けられるようにした
