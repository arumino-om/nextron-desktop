# 作業タスク

`docs/design-issues.md` が**決定と根拠**、この文書が**作業単位と受入条件**。

実装に入る前に必ず `design-issues.md` の該当箇所を読むこと。
ここに書いてあるのは「何をどこまでやれば終わりか」だけで、
**なぜそうするのかは一切書いていない**。根拠は常にあちら側にある。

## 0. 作業する人への前提

| | |

| `docs/design-issues.md` の該当する 詳細 節 | タスクの「参照」欄に書いてある |

### 0.2 環境

```sh
nix develop
cmake --preset arm64 && cmake --build --preset arm64
ctest --preset arm64          # 7 構成。全部通ること
```

### 0.3 仕様書の在りか

**仕様書そのものはリポジトリに入っていない**（§1 の「守る線」1.）。
タスクによって必要なものが違う。

| 必要なもの | 在りか | リポジトリに入っているか |
|---|---|---|
| API 名・引数・定数値 | `docs/api/{functions,constants,mtk3}.md` | **入っている** |
| オンディスク構造の byte offset | `design-issues.md` 詳細 C1 | **入っている** |
| 意味論の細部（待ち解除順・エラー条件等） | 仕様書本文 | **入っていない** |

本文が必要なタスクには「**原文必須**」と書いてある。その場合は
`BTRON_DOC` / `BRIGHTV_DOC` を設定して `tools/spec/html2text.py` を回すか、
既に変換済みの `.spec-work/text/`（gitignore）を使う。
**原文を持っていない場合、そのタスクは引き受けないこと。**
シグネチャだけ合っていて意味論が違う実装は、後で全部書き直しになる。

### 0.4 絶対に守ること

1. **`design-issues.md` に無い設計判断を勝手に下さない。**
   必要になったら**手を止めて、論点を §4 の一覧に追記する形で差し戻す**。
   勝手に決めると 2,600 行の決定群と乖離して、後から直すのが非常に高い。
2. **不変条件は文書上の約束にせず、テストにする。**
   `include/btron/test.h` の `BTRON_TEST` / `BTRON_CHECK` を使い、
   QEMU 上で実際に検査する。これは Phase 1 の ①〜⑮ が全部
   「無言のハング」から始まったことへの対処。
3. **コメントは日本語。** 既存のコードと密度・語り口を合わせる。
   「何をしているか」ではなく「**なぜそうしたか**」を書く。
4. **`EXPORT` / `IMPORT` / `LOCAL` / `CONST` を使う**（詳細 H7）。
   `static` / `extern` を直接書かない。
5. **コミットは分けない。** 1 タスク 1 コミット。

### 0.5 委譲可否の凡例

| | |
|---|---|
| ◎ | 独立。受入条件が機械的。並列に回せる |
| ○ | 独立。既存コードの形を真似る判断が入る |
| △ | API は仕様で決まっているが、他タスクと設計が噛む |
| ✗ | 決定が相互に絡む。切り出すとずれる |

## 1. タスクはどこにあるか

**タスク 1 件 = 1 ファイル。** `docs/tasks/<ID>.md` にある（W0-4）。
一覧は [`tasks/INDEX.md`](tasks/INDEX.md)（**生成物**。
`python3 tools/tasks_index.py` で作り直す）。

**なぜ分けたか。** 1 タスク 1 コミットで進めると、どの作業も必ずこの
ファイルの同じ領域（節の追加と状態表の行）を触る。実際、分ける前の
37 コミットは全部ここを触っていた。並列に進めると全員がぶつかる
（規律 **R29**）。

### 新しいタスクを足すとき

1. `docs/tasks/<ID>.md` を作る。先頭はこの形にする（ここだけ機械が読む）

   ```markdown
   # T9-99 なにかをやる

   - **状態**: 未着手
   - **委譲**: ○
   ```

2. 本文に「依存 / 参照 / やること / 触る / **受入条件**」を書く
3. `python3 tools/tasks_index.py` で索引を作り直す
4. 番号（システムコール番号・検査の order など）が要るなら
   [`registry.md`](registry.md) の**自分のレーンの帯**から取る

ID の割り当て。`T0-*` 基盤 / `T1-*` 中心核 / `T2-*` 周辺核 /
`T3-*` ファイルシステム / `T4-*` ディスプレイプリミティブ・画面 /
`T5-*` 外殻 / `W0-*` 並列作業のための下準備。

## 2. 層ごとの前提

### 中心核 (`T1-*`)

基準仕様は **μT-Kernel 3.0**（D10）。API は `docs/api/mtk3.md` の 240 件。
ランデブは μT-Kernel 3.0 の仕様には無く、**BTRON3 §1.3** の規定を使う（D10 の訂正）。

**T-License 2.2 のコードを取り込んではならない（規律 R15）。ヘッダも含む。**
仕様を読んで独自実装することだけが許される。

### 中心核と干渉しないもの (`T0-*` / `T2-01` / `T3-01` / `T3-02`)

ファイルシステムの交換形式コーデック・TRON コード変換表・FDT の汎用 API・
ライセンス境界の検査は他と干渉しない。**委譲するならここから。**

### 外殻 (`T5-*`)

E22 で「1 プロセス 1 サーバ」と決めてあるので、**1 マネージャ 1 レーン**が
そのまま成立する。ただし規約の細部は仕様原文にあるので、原文を持たない
作業者に渡してはならない（§0.3）。
