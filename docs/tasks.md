# 作業タスク

`docs/design-issues.md` が**決定と根拠**、この文書が**作業単位と受入条件**。

実装に入る前に必ず `design-issues.md` の該当箇所を読むこと。
ここに書いてあるのは「何をどこまでやれば終わりか」だけで、
**なぜそうするのかは一切書いていない**。根拠は常にあちら側にある。

### 0.3 仕様書の在りか

**仕様書そのものはリポジトリに入っていない**（§1 の「守る線」1.）。
タスクによって必要なものが違う。

| 必要なもの | 在りか | リポジトリに入っているか |
|---|---|---|
| API 名・引数・定数値 | `docs/api/{functions,constants,mtk3}.md` | **入っている** |
| オンディスク構造の byte offset | `design-issues.md` 詳細 C1 | **入っている** |
| 意味論の細部（待ち解除順・エラー条件等） | 仕様書本文 | **入っていない** |

本文が必要なタスクには「**原文必須**」と書いてある。その場合は
`BTRON_DOC` / `BRIGHTV_DOC` を設定して `tools/spec/html2text.py` を回すか、
既に変換済みの `.spec-work/text/`（gitignore）を使う。
**原文を持っていない場合、そのタスクは引き受けないこと。**
シグネチャだけ合っていて意味論が違う実装は、後で全部書き直しになる。

### 0.4 絶対に守ること

1. **`design-issues.md` に無い設計判断を勝手に下さない。**
   必要になったら**手を止めて、論点を §4 の一覧に追記する形で差し戻す**。
   勝手に決めると 2,600 行の決定群と乖離して、後から直すのが非常に高い。
2. **不変条件は文書上の約束にせず、テストにする。**
   `include/btron/test.h` の `BTRON_TEST` / `BTRON_CHECK` を使い、
   QEMU 上で実際に検査する。これは Phase 1 の ①〜⑮ が全部
   「無言のハング」から始まったことへの対処。
3. **コメントは日本語。** 既存のコードと密度・語り口を合わせる。
   「何をしているか」ではなく「**なぜそうしたか**」を書く。
4. **`EXPORT` / `IMPORT` / `LOCAL` / `CONST` を使う**（詳細 H7）。
   `static` / `extern` を直接書かない。
5. **コミットは分けない。** 1 タスク 1 コミット。

### 0.5 委譲可否の凡例

| | |
|---|---|
| ◎ | 独立。受入条件が機械的。並列に回せる |
| ○ | 独立。既存コードの形を真似る判断が入る |
| △ | API は仕様で決まっているが、他タスクと設計が噛む |
| ✗ | 決定が相互に絡む。切り出すとずれる |

  （キーボード / 絶対座標 PD / 相対座標 PD）

**なぜ virtio-mmio か。** arm64 の QEMU virt 機種には PS/2 が無い。
PCIe は列挙と割込み経路（INTx の _PRT か MSI-X の ITS）が要り、USB は
もっと重い。virtio-mmio は枠が Device Tree に全部書いてあり、割込みも
普通の SPI なので、**アドレスも割込みも記述から取れる（規律 R19）**。

**キートップコードは evdev のキーコードをそのまま使うと決めた。**
仕様 §1.7.3 は「キーボードにより規定される」として値を定めていない。
evdev のコードは元々「キーの物理的位置」の番号で意味が一致し、0〜255 に
収まって `KEYMAX` = 256 と合う。`KeyTab` は「evdev コード → TRON 文字
コード」の表になる。

**役割の分け方。** 配列を知っているのはドライバだけなので、
「どのキートップがシフトか」はドライバが決め (`evt_meta`)、
文字コードへのエンコード・キュー・自動リピート・ボタン状態は周辺核が
持つ (`evt_key` / `evt_pd_*`)。

- **既知の制限**
  - 旧式インタフェース（MMIO Version 1）は扱わない。QEMU は既定で
    旧式を出すので `-global virtio-mmio.force-legacy=false` が要る
    （`run_qemu.py --input` が面倒を見る）
  - ACPI 経路では枠の記述が DSDT の AML の中にあり読めない → T1-15
- **受入条件**（すべて通過）
  - ctest の `input-arm64` 構成で「入力枠 2 台」＝「入力装置 2 台」
    （見つけた台数と動かせた台数が一致すること）
  - キーボードが `"kbd"`、PD が `"pd"` でデバイス管理に出ること
  - 既定の変換表で evdev 30 番が `'a'`、左シフトで `'A'`、
    命令シフトで `0x01` になること
  - **マスクで消されてもキー状態配列は更新される**こと
