# 並列開発の計画

**複数の作業を同時に走らせる前提で、何から手を付けるかを決めた文書。**
決定と根拠は [`design-issues.md`](design-issues.md)、作業単位と受入条件は
[`tasks/`](tasks/)、番号の予約は [`registry.md`](registry.md)。
ここにあるのは**順番と分担**だけである。

## 1. いまどこまでできているか

四層のうち**下 3 層は通っていて、最上層（外殻のマネージャ群）がほぼ空**。
arm64 は QEMU 9 構成で検査 174 件＋自立起動 29 件、**x86_64 は起動・
ページング・例外まで（不変条件 24 件）** が通る。

`docs/api/functions.md` の抽出 API に対する実装率（名前の有無で数えた概算。
`map_rec` のような `ER_NOSPT` スタブも「有り」に数えているので少し甘い）。

| 層 | 実装/全 | 残りの中身 |
|---|---|---|
| 周辺核 (第1章) | **125/143** | §1.5.4 の `malloc` 族（ライブラリ）・`def_exc` / `ret_exc`・`map_rec` |
| ディスプレイプリミティブ (第2章) | **56/105** | 曲線・楕円・弧・多角形・ピッキング・回転・`GRGN`・カラーマップ |
| 外殻 (第3章) | **37/244** | WM が 37/50。**他 10 マネージャは 0/194** |
| ライブラリ (第2編) | **4/368** | `bstdio` / `bstdlib` / `bmath` / `tstring` / `libwin` ほぼ全部 |
| 超漢字 オブジェクト ID | 22/66 | |
| 合計 | **約 246/998** | |

**自立起動の芯は通った（T3-03）。** virtio-blk ドライバと GPT の区画表、
起動列 (`sys_startup()`) が入り、**ディスクから起動して前回の内容が残り、
ディスク上の実行プログラムから外殻が起きる**ところまで動く
（`ctest` の `selfboot-arm64` が同じイメージで 2 度起動して確かめる）。
残っているのは `/SYS/DEVCONF` の書式（仕様原文が要る）と、
**起動列から外殻を常駐させて居座る**経路 — いまは検査が終わると
`hal_exit()` する。

## 2. 完成の定義

| | 中身 | 残量の目安 |
|---|---|---|
| **M1 自立起動** | ~~ブロックデバイス ＋ GPT の BTRON 区画 ＋ 永続 FS~~（T3-03 で完了）＋ `/SYS/DEVCONF` ＋ 外殻を常駐させる起動列 ＋ EL0 のシェルが居座る。**検査からではなく、ディスクから起動して画面が出たまま動き続ける** | 残り 3〜5 タスク |
| **M2 GUI 一式** | DP の図形と `GRGN`、WM の残り 13 本 ＋ ポップアップ面 (E21)、マネージャ 10 本、データボックス、アプリケーション登録 (E14) | 25〜35 タスク |
| **M3 実用** | TAD (B5) → 基本文章エディタ → TIP と日本語入力 → 小物・設定パネル・ディスク整理 (C4) | 15〜25 タスク |
| **M4 移植性と堅牢性** | x86_64（起動は完了。中心核の接続が残り）、SMP、タスク例外、ACPI の AML、サーバ復旧 (E23)、ジャーナリング (C9) | 残り 7〜11 タスク |

ライブラリ 368 本は量が多いだけで機械的なので、どのマイルストーンにも挟める。

**完成に入れないもの**（§1 のライセンス方針）: GT書体・大漢和の字形、
日本語入力辞書のデータ。別途ライセンスが必要で、仕様文書と同じ扱いにする。

## 4. レーン

判断が入る / △ 他と設計が噛む / ✗ 切り出すとずれる）。

## 5. 先に下しておく設計判断

`tasks/` の規律「**`design-issues.md` に無い設計判断を勝手に下さない。
手を止めて差し戻す**」は並列でも変えない。変えないからこそ、
**着手前に決めておかないとレーンが止まる**。

| 判断 | 誰が待っているか |
|---|---|
| A13 ページサイズ（4KB / 16KB） | L5（x86_64 は 4KB 固定。arm64 の選択と揃えるか） |
| A4 エンディアンと準規格 | L1（交換形式は両方を読む） |
| E8 任意領域 `GRGN` の実装方式 | L4 / L9 |
| E7 アルファ合成・アンチエイリアス | L4（仕様に概念が無い。拡張設計が要る） |
| E9 高DPI / E10 複数ディスプレイ | L9 |
| E11 テーマ機構 `WI_*` | L9 / L8b |
| E12 `osta_prc` / `oend_prc` の契約 | L8 全部 |
| E13 `oreq_prc` / `orsp_prc` の同期要求 | L8a / L8f |
| E14 アプリケーション登録・実行環境ファイル | L8a / M1 の起動列 |
| E15 付箋の 4 種類 | L8a |
| E21 ポップアップ面（決定済。実装が要る） | L8c / L8d / TIP |
| E23 サーバの異常終了と復旧 | L9 |
| B5 TAD セグメント一覧 | Wave 3 全部 |
| C9 ジャーナリング | M4 |
| F1 ユーザランドドライバ | L6（いまはカーネル内。出すかどうか） |

**運用:** 設計レーンを 1 本常駐させ、**`design-issues.md` はそのレーンだけが
書く**。止まったレーンは論点を §4 の一覧の形で差し戻し、決定が書かれてから
再開する。こうしないと 290KB の決定群と実装が乖離する。

## 6. Orca での運び方

| | |
|---|---|
| ブランチ | 1 レーン 1 ブランチ。`<作業者>/<レーン名>`（例 `arumino-om/l6-selfboot`） |
| コミット | **1 タスク 1 コミット**（`tasks/` の規律 0.4-5）。タスクのファイルと同じコミットで状態を更新する |
| 受入 | `ctest --preset arm64` が**全構成**通ること（いま 11 件）。x86_64 を触るなら `ctest --preset x86_64` も。逆テストを 1 つ添えること |
| マージ順 | W0 → L6（土台）→ その他。L6 が動いた日は L6 を先にマージする |
| 番号 | [`registry.md`](registry.md) の自分の帯だけから取る |
| 検査 | `src/kernel/core/tests/<区分>.c` を新規に作る。既存の区分には足さない |
| ソース | 自分のディレクトリの `sources.cmake` にだけ足す |
| 索引 | `docs/tasks/INDEX.md` は**生成物**。衝突したら `python3 tools/tasks_index.py` で作り直す（解決が自明になる） |
| 設計 | `design-issues.md` を触るのは設計レーンだけ |

**同時に走らせるレーンの数は 4〜6 本を目安にする。** 各レーンが QEMU で
9 構成を回すので、それ以上は検査が詰まる。委譲 ✗ のレーン（L6 / L10）は
同時に 1 本までにする。

## 7. 作業環境

`nix develop` が本来の経路（`flake.lock` で clang 21 / QEMU / OVMF /
Unifont まで固定される）。それが無い環境向けの逃げ道は README の
「nix を使わない場合」にある。**どちらでも `ctest --preset arm64` が
全構成通ることが受入条件**で、そこは環境で変わらない。

**仕様原文はリポジトリに無い**（§1 の守る線）。`docs/api/` のシグネチャは
コミットしてあるので Wave 1 は動くが、外殻のマネージャ（第3章）は規約の
細部が原文側にある。Wave 2 を始める前に `BTRON_DOC` / `BRIGHTV_DOC` を
各ワークツリーから見える所に置くこと。**原文を持たないレーンに
「原文必須」のタスクを渡してはならない**（`tasks/` の 0.3）。
